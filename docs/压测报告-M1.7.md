# b-artifact 压测报告 · M1.7（历史修订列目录）

**日期**：2026-09-15
**范围**：M1.6 唯一未达标项 —— 非 HEAD 修订的列目录（`list_dir_at` / `tree?rev=N`）
**结论**：`tree?rev=<旧修订>` 端到端 **6557.6 ms → 15.8 ms（416×）**；`m` 档下
"选中最新修订"从 **7.4 s → 0.05 ms**。复杂度从 **O(该前缀下的全部历史)** 降到
**O(直接子项 + (rev, head] 的增量)**。顺带修掉一个**数据正确性 bug**（`head_entries.changed_rev` 在存量库里全是 head_rev）。

> 前序：[压测报告-M1.5.md](压测报告-M1.5.md)（四档实测与 B1~B6）、[压测报告-M1.6.md](压测报告-M1.6.md)（B1/B2/B4/B5/B6 修复与三档回归）。
> 本报告只讲 M1.6 留下的那一项。

---

## 1. 问题与三个根因

M1.6 的结论是：非 HEAD 列目录 **m 档 7.4 s（只快 3.0×）**，按跨档位代价模型外推
**full 档约 29 s**，且"仍是 O(仓库规模)"。这轮把它拆开看，发现是**三个独立原因叠在一起**。

### 根因 ① `rev >= head_rev` 也去回放历史（没有 HEAD 快路径）

`list_dir_at` 无条件走"枚举 changes 推导状态"，而 `rev == head_rev` 时结果与
`list_dir_head`（`head_entries` 的 `parent_path` 等值查询，O(直接子项)）**完全等价**。

API 层对 `rev == 0 || rev == head_rev` 有短路，所以这个洞在 HTTP 路径上暂时看不出来；
但**压测 harness 直接调 `list_dir_at(rev=head_rev)`**，量出来的 7.4 s 就是这一条。
它也是真实的隐患：任何直接调用方（含将来的批量导出/镜像工具）都会踩到，
而 `rev > head_rev` 的请求在 API 上**不受短路保护**，此前同样是 7 秒级。

### 根因 ② 历史路径枚举"整棵子树"，再逐条复核

旧实现：

```
last_changes_under(prefix, rev)   → 该前缀下**每个路径**的最后一次变更（O(子树历史)）
for 每条候选:  file_at / dir_explicit_alive（1 次点查）
             + covering_tombstone（深度次点查）
再把这些候选归约成"直接子项"
```

要输出的只有**几十个直接子项**，却做了 O(子树) 的工作：24 万文件档位下
`list_dir_at_l2_mid`（prefix=`assets/0000`）实测 **158 ms**，其中绝大部分是
"4 万条候选 × 每条的 2~5 次索引点查"。候选枚举本身（那条 `changes` 查询）在
sqlite3 里直接量是 0.6 s（整仓范围），去掉窗口函数排序后是 0.2 s 级。

### 根因 ③（数据 bug）`head_entries.changed_rev` 在存量库里不可信

为了修 ②，新算法需要"这个条目的内容最后一次变化的修订"作为廉价判据 ——
也就是 `head_entries.changed_rev`。差分验证立刻发现**它在老库里是错的**：

```
m 档 fixture（24 万文件 / 2 万修订）：
  head_entries 共 265,641 行，changed_rev **全部 = 20000**（当时 head_rev）
  而 assets/0000/0000/000/f00.bin 的真实历史是 add@1 / modify@3551 / modify@14024
```

即 M1.5 时代的一次批量回填把整张表刷成了当时的 head_rev。当前代码的提交路径是
**正确**的（干净实验：a.txt=2 / b.txt=1 ✓），所以这是一个"存量数据被污染"的问题。
但 `changed_rev` 是**对外可见字段**（`tree` 响应带它，管理端与客户端的历史明细都展示
"最后变更修订"），所以错值本身就是 bug —— 那些界面上此前会全显示同一个 rev。

## 2. 修复

### ① HEAD 快路径

```rust
let head_rev = repo_head_rev(conn, repo_id)?;
if rev >= head_rev { return list_dir_head(conn, repo_id, prefix); }   // O(直接子项)
```

`rev > head_rev` 也一并覆盖：历史里没有更大的修订，结果与 HEAD 相同。

### ② 历史路径：候选降级为"直接子项"

```
候选 = HEAD 的直接子项（parent_path 等值，O(直接子项)）
     ∪ (rev, head] 内被删除的路径的一级子段（走 idx_changes_rev 的区间扫描）
```

对每个候选判定"在 rev 时是否存在"：

| 情形 | 判定方式 | 代价 |
|---|---|---|
| 文件，且 `changed_rev <= rev` | 直接采用 HEAD 行 | O(1) |
| 文件，其他 | `file_at(path, rev)` 点查（含祖先 Tombstone） | O(log n) |
| 目录 | ① HEAD 目录行的 `changed_rev <= rev` → 存在<br>② 否则子树里存在 `changed_rev <= rev` 的**文件行** → 存在<br>③ 否则看 `(rev, head]` 内该子树被删路径是否在 rev 时存活<br>④ 兜底 `dir_explicit_alive`（显式空目录） | ②是 LIMIT 1 的范围扫描，命中即停 |

**成立依据**：HEAD 里现存的条目，其 `changed_rev` 就是它最后一次 add/modify 的修订；
真被删过又重建的话，`changed_rev` 会变成重建那次（> rev）。所以
`changed_rev <= rev` ⟹ 该条目在 rev 时已存在。

### ③ 迁移 006：重算文件行的 `changed_rev`

```sql
UPDATE head_entries SET changed_rev = (SELECT MAX(c.rev) FROM changes c
        WHERE c.repo_id = head_entries.repo_id AND c.path = head_entries.path)
 WHERE kind = 'file' AND EXISTS (...);
```

只重算**文件行**：文件在 `changes` 里必然有自己的行，`MAX(rev)` 是准确答案；
目录行的 `changed_rev` 是"物化时顺带记下的子项 rev"，语义本就模糊（既有行为，不动）。
幂等，取值为 `changes` 的函数，重复执行结果相同。24 万行实测 **2.2 s**。

### ④ 顺带：去掉排序、修正"把自己列出来"

- `last_changes_under` 的窗口函数（`ROW_NUMBER() OVER (PARTITION BY path ORDER BY rev DESC)`）
  会**物化整个区间再排序**；改成 `GROUP BY path` + 裸列配 `MAX(rev)`，可直接顺
  `idx_changes_path(repo_id, path, rev DESC)` 的顺序分组，**不排序**。
  （该函数仍被 `has_alive_descendant` / `restore` 使用。）sqlite3 直测：整仓范围 2.79 s → 0.60 s。
- 旧实现在 prefix 自身也是候选时，会把**前缀目录自己**列进结果（调用方得自己过滤，
  管理端与客户端都写了 `items.filter(i => i.path !== prefix)` 来兜）。
  新实现只列直接子项，这个瑕疵自然消失。

## 3. 验证

### 3.1 差分验证（新工具 `scripts/verify_list_dir_at.py`）

单测只覆盖小规模场景，这条路径的重写必须**在真实规模上逐步比对**。脚本做三件事：

1. 用 SQLite 按**旧语义**（窗口函数枚举 + 逐候选 `file_at`/`dir_explicit_alive` + 祖先
   Tombstone + 归约）算出参考结果；
2. 调服务端 `GET /tree?prefix=&rev=&depth=1` 取新实现的输出；
3. 逐条比对路径集合。

在 m 档 fixture 上，5 个修订（`head` / `head-1` / `mid` / `head/10` / `1`）× 6 个前缀
（根 / 三层目录 / 叶子 / 不存在）= **30 组全部一致**：

```
✓ rev=20000 (HEAD) prefix='assets/0000/0000'            旧 15 条 / 新 15 条
✓ rev=10000        prefix='assets/0000/0000/000'        旧 10 条 / 新 10 条
✓ rev=1            prefix='assets/0000'                 旧 14 条 / 新 14 条
...
---- 差分结果：30 / 30 组完全一致 ----
```

参考实现踩过两次坑，都记在脚本注释里：**必须逐字复刻被参照的语义** ——
① 漏了 `normalize_prefix`（前缀要补尾斜杠）；② `prefix_bounds` 的入参必须是**已归一化**
的前缀、上界 = 末字节 +1。参考实现写错会把"实现错"误报成"实现错"。

## 5. 现在的复杂度与已知边界

- **HEAD 修订**：O(直接子项)，与仓库规模无关。
- **历史修订**：O(直接子项) + O(`(rev, head]` 内的删除行数) + 少量点查。
  **与子树规模无关**（这是与旧实现最关键的区别）。
- **已知边界**：`(rev, head]` 的增量上界是"这段区间内的历史"。若某仓库**删除极其频繁**
  且查询的修订很旧，增量会变大，最坏退化到"与这段历史成正比"（仍比旧实现少掉排序与
  逐条复核）。**本轮的 m 档 fixture 不含删除操作**（`被删除过的路径数 = 0`），
  所以这部分代价被低估了 —— 造一个"高删除率"的 fixture 才能真正压出上界，列为后续项。
- **一个行为变更（修正）**：列目录不再把"前缀目录自己"列进结果（旧实现会，
  调用方需自行过滤）。管理端与客户端本来就写了过滤，无影响。
- **一个数据修正**：迁移 006 会把存量库里被污染的 `head_entries.changed_rev` 修正；
  一次性、幂等，24 万行 2.2 s。
