# b-artifact 架构设计方案

> 一个面向**二进制资产**的类 SVN 集中式版本管理系统
> 服务端 Rust ｜ 管理端 Vue 3 ｜ 客户端 Electron

版本：v0.4.17（需求变更轮：锁模型收敛 + 口令策略 + 客户端工作副本重做）
日期：2026-09-15

修订记录：
- v0.4.17：**需求变更轮（M4.8）—— 8 项来自真实使用的反馈，其中 3 项改变了系统语义**。
  ① **锁模型收敛**：删掉 `advisory` 策略与 `dir` 锁。"先锁后提交"变成唯一语义 —— 每个变更路径都必须由**本人持锁**（原 `strict + needs_lock=glob` 的"部分文件要锁"也一并去掉，`repos.lock_policy` / `repos.needs_lock` 两列废弃、恒写 `strict` / `''`）。建仓不再让用户选策略（§5.1/§5.2/§5.3 重写、§3.2 字段废弃、§7.2 接口收紧）。**收益是两处实质简化**：锁查找不再需要沿祖先链回溯（原本每次提交对每个路径要做 N 层点查），强制解锁不再有"子树连带强制解锁"，purge 的前置校验也从"该前缀下有没有他人锁"退化成单点查。
  ② **口令策略**：新增唯一入口 `auth/password.rs::validate_policy()` —— 长度按**字符** ≥8 且 ≤256、且必须同时含数字/大写/小写/符号四类。此前四处校验都是 `String::len() < 8`（**数的是字节**，3 个汉字即通过）且无复杂度要求，已全部替换（§9.2）。
  ③ **客户端工作副本重做**：平铺状态表 → **目录树**（全量树 + 状态/锁标记 + 目录汇总"变更 N"，默认只展开有变更的分支）；「刷新状态」按钮删除，改为主进程 `fs.watch` 递归监听 + 300ms 防抖**自动同步**（失败降级为隐藏的手动刷新）；「标记新增」按钮删除（未纳管文件直接算新增，但**默认不勾选**，需用户确认）；提交说明可空（服务端本就接受空 message）；目录树内可直接**新建文件/文件夹/删除**；加锁入口从独立「锁」视图搬进工作副本（§6.5）。
  ④ 其余四项：管理端仓库列表「先锁后提交」列**空白标签**的根因是**同一字段两套语义**（DB 默认 `''` 而详情页按 `never|auto|always` 枚举写）—— 随①一并删除该列与设置项；用户信息去掉邮箱（API 与界面不再出现，DB 列保留不写入）；工作副本页新增「打开已有副本」（最近列表 + 浏览目录，复用既有 `wc:recent`/`wc:open`）；管理端建仓表单只剩名称与描述。

## 1. 项目概述

### 1.1 定位

面向**美术资源 / 设计稿 / 工程文件 / 影音素材**等以二进制为主、单文件体积大、无法自动合并的场景，提供一套集中式（Centralized）版本管理服务。

与 Git 的根本差异不在于"谁更好"，而在于**模型的适用性**：

| 维度 | Git 模型 | 本项目（SVN 模型） |
|---|---|---|
| 仓库位置 | 每个开发者一份完整历史 | 服务端唯一权威，客户端只有工作副本 |
| 二进制处理 | 每次改动全量存对象，克隆成本爆炸 | 内容寻址 + 去重，天然适合大文件 |
| 权限 | 服务端仅有"读写"粗粒度 | **按目录**细粒度授权，可下发/可审计 |
| 并发编辑 | 事后合并（二进制无法合并） | **先锁后改**，从源头避免冲突 |
| 部分获取 | 需 partial clone + sparse-checkout，能力有限 | **目录级部分检出**是一等公民 |
| 离线性 | 完整本地历史，完全离线 | 依赖服务端（本项目用本地元数据做缓冲） |

### 1.2 核心能力（v1 范围）

1. **二进制优先的存储**：内容寻址存储（CAS），字节级精确还原，跨修订/跨仓库自动去重。
2. **文本文件同样支持**：文本文件享受行级 diff 与自动合并；存储层与二进制完全统一。
3. **目录级权限**：仓库内任意目录配置 read / write / admin 三级权限，主体支持用户、用户组、所有人。
4. **按目录拉取**：客户端可选择只检出某个子目录（部分检出的工作副本），更新时只拉取该子树。
5. **锁定式并发编辑**：按**文件**加锁，先锁后提交 —— **提交时每个变更路径都必须由本人持锁**，否则整单拒绝（v0.4.17 收敛，原"严格/建议两种模式"与目录锁一并删除，见 §5.1/§5.2）；支持强制解锁与审计。
6. **按目录清理**：两级语义——①普通删除（进入历史、可追溯、可还原）；②**清除历史**（管理员级，把某文件/目录连同其全部修订记录从服务端彻底抹除并回收磁盘）。
7. **服务端管理页面**：Vue 3 实现，用户/组/仓库/权限矩阵/锁/审计/存储用量/内容清理。
8. **Electron 桌面客户端**：工作副本管理、状态视图、提交/更新/加锁（文件或目录）、传输进度、冲突处理。
9. **统一认证**：本地账号 + LDAP 双来源登录；LDAP 用户**登录即自动建号**；系统中**第一个登录的用户自动成为系统管理员**。

### 1.3 非目标（v1 明确不做）

- 分支/合并（branch & merge）。v1 单主干线性历史，标签通过修订号 + 目录约定实现。
- 分布式/离线提交（无本地历史，客户端断开即无法提交）。
- 二进制文件的行级 diff / 三方合并（业界无可靠方案，改为锁 + 冲突备份）。
- 跨仓库原子提交（subversion 的 externals / git 的 submodule 均不做）。

### 2.1 为什么是"集中式"

本项目采用集中式的**根本原因就是需求本身**：按目录配置权限、按文件/目录加锁。

- 这两项能力都要求服务端是**唯一权威**：权限在每次请求时由服务端强制校验，客户端持有的任何凭据都无法绕过目录 ACL；锁由服务端登记与仲裁，是权威约束而非建议。
- 分布式模型（Git）中，服务端只是众多对等副本之一，历史与内容落在每个人手里，**目录级授权与锁最多只能是"建议"**（Git 的 hook/gatekeeper 方案本质上是绕道集中化，且覆盖不了直推仓库的场景）。
- 相应的代价也由这个选择天然确定：客户端没有完整历史，离线只能缓冲、不能提交（见 §1.3 非目标）；这是用"离线性"换"权限与锁的强制性"，对本项目的场景是划算的。

### 2.2 关键技术决策（详见 §14）

| 决策 | 选型 | 理由 |
|---|---|---|
| 服务端框架 | axum 0.8 + tokio | 生态成熟、tower 中间件、性能好 |
| 元数据库 | SQLite（rusqlite bundled，WAL） | 零运维、单文件、支持大仓库；接口收敛便于换 PG |
| 内容存储 | 文件系统 CAS（sha256 两级目录） | 支持 sendfile 零拷贝、易备份、天然去重 |
| 压缩 | zstd（auto 策略，仅当收益 > 5%） | 文本/日志类资产省 60%+，二进制无收益时自动跳过 |
| 认证 | 本地账号(argon2id) + LDAP 双来源 → opaque token | 企业统一账号走 LDAP，登录即建号（JIT）；`AuthProvider` 抽象，OIDC 留扩展位 |
| 管理端 | Vue 3 + Vite + TS + Pinia + Element Plus | 表格/表单密集型后台，开发效率最高 |
| 客户端 | Electron + Vue 3 | 已指定；跨平台、生态成熟 |
| 传输 | HTTP/1.1 REST + 原始 body | 可被任意代理/网关承载，调试成本低 |

### 3.1 存储布局

```
data/
├── b-artifact.db                  # SQLite（WAL 模式）
├── b-artifact.db-wal
├── blobs/                      # 内容寻址存储
│   ├── 3f/

**写入原子性**：上传 → 写 `tmp/<uuid>` → 计算 sha256 校验 → `fsync` → `rename` 到 `blobs/xx/yy/<hash>`。`rename` 在同一文件系统内原子，因此不存在"半个 blob"可见的状态。

**分片目录深度**：2 级共 4 位十六进制 = 65536 个目录，单目录约 15 个文件（千万级 blob 规模），兼顾 `readdir` 性能与目录数上限。

### 3.3 修订与清单模型：路径历史（Path-History）

**问题**：每个修订存一份完整清单，10 万文件 × 1000 修订 = 1 亿行，不可行；但"取修订 N 的目录树"和"取修订 N 的文件内容"又是最高频操作。

**方案**：只存增量变更（`changes` 表），由变更序列推导任意修订状态。核心约定（v0.4 定死）：

- **目录 Tombstone**：删除目录只写一行 `(rev, path=目录, op='delete', kind='dir')`，**不展开**逐文件 delete。该行覆盖整棵子树在 ≥rev 之后的所有路径。逐文件展开会让"删除含 10 万文件的目录"产生 10 万行变更，且恢复时无从区分"显式删除"与"随目录消失"。
- **目录行的记录时机**：`kind='dir'` 的行**只在显式目录操作时出现**——add dir（mkdir）、delete dir（rmdir，含递归删除）、purge、显式空目录提交。文件的 add/modify 不产生父目录行；目录存在性由"其下任一存活文件 + 未被 Tombstone 覆盖"推导。
- **恢复 = 新提交**：`restore(path, source_rev)` 只是把 source_rev 时该路径的内容以 add/modify 写入**新修订**，不产生任何"反向变更"。好处：历史永远线性只增，"恢复"本身可追溯、可再次恢复，与权限/锁校验走完全相同的提交流程。

**存在性判定**（给定 path 与 rev N）：

1. 取 `path` 自身最近一次 change（`rev <= N`，按 `idx_changes_path` 一次点查）；
2. 沿祖先链取每个祖先目录最近一次 change；
3. 若任一祖先是 `op='delete', kind='dir'` 且其 rev **晚于** path 自身最后一次有效 change，则路径不存在（被 Tombstone 覆盖）；
4. 否则按 path 自身最近一次 change 判定：`op='delete'` 不存在；`op='add'|'modify'` 存在；dir 行存在但目录可能为空（允许空目录）。

祖先链深度 = 目录深度（≤ 数十），全部为索引点查，成本可忽略。

**核心查询**：

- **取某文件在修订 N 的内容**（最高频，O(log n)）：
  ```sql
  SELECT blob_hash FROM changes
   WHERE repo_id=? AND path=? AND rev<=? AND kind='file'
   ORDER BY rev DESC LIMIT 1;
  ```
  命中 `idx_changes_path` 索引，等价于一次 B 树查找。

- **取修订 N 的某目录列表**（列目录，处理 Tombstone 后行内去重）：
  ```sql
  WITH last AS (
    SELECT path, op, kind, size, mode, blob_hash,
           ROW_NUMBER() OVER (PARTITION BY path ORDER BY rev DESC) AS rn
      FROM changes
     WHERE repo_id=? AND rev<=?
  )
  SELECT * FROM last WHERE rn=1 AND op<>'delete' AND path LIKE ?prefix;
  -- 服务端在结果上再过滤一次：被 delete dir Tombstone 覆盖的文件行剔除
  ```

- **取两个修订之间的差异**（更新用，只传变化）：
  ```sql
  SELECT path, op, kind, size, blob_hash FROM changes
   WHERE repo_id=? AND rev>?from AND rev<=?to ORDER BY rev;
  ```
  客户端 update 时按 §3.3 存在性判定折叠 Tombstone（delete dir 即对本地对应子树整体删除）。

**manifest_hash 降级（v0.4）**：原设计"每修订一份全量清单滚动哈希"隐含要求提交时生成全量清单，与 Path-History 的 O(变更数) 提交目标矛盾。降级为：

- 仅 **HEAD 修订**在提交完成后由后台异步计算 `manifest_hash`（`sha256(排序后的 "path\0hash\n" 拼接)`），用于完整性巡检（`admin/maintenance` 定期校验 HEAD 树）。
- 历史修订不保证有值（新建仓库为空；purge 重算时仅同步 HEAD）。
- 真正的"每目录增量完整性校验"（Merkle 树）列为 **P2 未来项**（§15.3），v1 不做。

**取舍**：列目录（历史修订）是范围扫描，比"快照表"慢；但快照表会让提交写入放大到 O(文件总数)。我们选择**优化高频提交 + 高频单文件读取**，并把"历史修订列目录"列为低频操作。

**HEAD 树加速**：维护 `head_entries(repo_id, path, ...)` 一张随提交就地更新的表。日常的"列目录/取文件"直接打这张表（O(log n) 主键查找），历史修订才走上面的推导路径。HEAD 的目录删除直接物理删除子树行（Tombstone 在 HEAD 不留行），空间成本 = 文件总数（10 万行，微不足道）。

### 3.4 二进制处理策略

| 环节 | 做法 |
|---|---|
| 存储 | 整文件存储，**不做二进制 delta**。保证字节精确、实现简单、并行友好 |
| 去重 | sha256 内容寻址；同一份素材在 100 个修订中出现只占 1 份磁盘 |
| 压缩 | `auto`：按采样判断可压缩性，仅当 zstd 体积 ≤ 原体积 95% 时才存压缩版，`blobs.codec` 记录；读取时透明解压 |
| 上传 | 先问后传（`blobs/missing`），幂等（同 hash 重传直接返回 ok） |
| 下载 | `raw` blob 支持 HTTP `Range`（大文件断点续传）；`zstd` blob 忽略 Range 返回全量（M1 简化，服务端流式解压不支持区间）；`ETag` = blob hash，天然强缓存 |
| 完整性 | 上传时服务端重算 sha256 校验；下载时客户端校验；不一致即拒绝落盘 |
| 大文件 | ≥ 64 MB 走分块上传（协议见 §7.2，**M1 起实现**，不做降级方案） |

**为什么不做 delta**：xdelta/bsdiff 类算法对 4K 视频、PSD 这类改动分布广的二进制收益不稳定，且会把"取文件"从一次读取变成一条 delta 链的串行重放（历史越长越慢）。CAS 全量 + 去重已经覆盖了主要收益（工程文件只改一部分、其他文件不变时收益是 100%）。

### 3.6 内容生命周期：删除、清理与历史清除

对"文件及其历史"的处理必须区分**两级语义**，管理页与客户端都要明确标注，避免误操作：

| 级别 | 名称 | 语义 | 可逆性 | 权限 |
|---|---|---|---|---|
| L1 | **删除**（delete） | 新修订中标记 `op=delete`。历史修订中仍可取回旧版本 | 可逆（还原该路径到旧修订即可） | 目录 `write` |
| L2 | **清除历史**（purge） | 把该路径在**所有修订**中的记录连同内容一并从服务端抹除，之后任何修订都无法再取回 | **不可逆** | 目录 `admin` + 系统管理员二次确认 |

L1 就是普通的提交删除（走 §5.3 提交流程），这里不赘述。L2 是一个独立的服务端维护操作：

**清除历史（purge）流程** —— 事务内完成，期间仓库进入维护态（拒绝新提交，读不受影响）：

1. **前置校验**：请求者对该目录有 `admin` 权限且是系统管理员；提供 `reason` 必填；该前缀**及其子树**内若存在他人持有的有效锁则**拒绝**（提示先强制解锁），本人锁自动释放并记审计。**v0.4.17 简化**：锁只剩文件级，此处是"按路径前缀范围扫 `locks`"的单次查询，不再需要 dir 锁的递归覆盖判定。
2. **删除路径历史**：`DELETE FROM changes WHERE repo_id=? AND (path=? OR path LIKE ?/%)`；同步删除 `head_entries` 中对应行。注意 purge 与普通删除（L1）的语义差异：purge 是彻底抹除，**不写 Tombstone**，路径如同从未存在过。
3. **修订统计修正**：对受影响的每个修订，重算 `file_count`、`byte_delta`（由剩余行聚合）；`manifest_hash` 仅 HEAD 重算（历史修订按 §3.3 降级不保证）。
4. **引用计数回收**：`refcount` 是可重建缓存，purge 后按新 `changes` 重建受影响仓库的计数；降为 0 的 blob 进入 GC 队列。
5. **审计**：记录 purge 操作的完整快照清单（路径、修订范围、涉及 blob 数、预估回收字节）到审计日志，供追溯"删了什么"（内容本身不再保留）。

**返回摘要**：`{ paths_removed, revisions_affected, blobs_reclaimed, bytes_reclaimed, gc_scheduled_at }`。

**实现要点**：purge 的成本与"该前缀出现过的修订数"成正比，与仓库总修订数无关，因此对大仓库也是可控的。purge 期间对同一仓库加写互斥（与提交共用 `head_rev` 乐观锁通道），避免出现"purge 到一半，新提交又写回同前缀"的竞态。

### 3.7 Blob 全局生命周期与 GC（v0.4 重写）

blob 跨仓库内容去重，**不属于任何仓库**，因此 GC 是全局的（`gc_queue` 无 repo_id）：

```
PUT 成功 ──────────────► blobs(refcount=0)  ← orphan 状态，属**正常路径**
                             │
   被提交引用 ──────────────►│ refcount↑（缓存更新，可重建）
   提交删除/取消 ──────────►│ refcount↓
                             ▼
                     refcount==0 且无 pending_commit 引用
                             │  进入 gc_queue（宽限期默认 24h）
                             ▼
                     到期 + 最终复查通过 ──► 物理删除磁盘文件
```

**关键语义**：

1. **orphan blob 是正常的**：`PUT /blobs` 成功但提交从未落地（客户端取消、网络中断、prepare 过期）是最常见路径。orphan 不需要特殊处理——它 refcount=0，走统一的 GC 队列，宽限期后回收。
2. **`changes` 表是引用事实来源**：`blobs.refcount` 只是**可重建的缓存**。任何"refcount 与实际引用不一致"的场景（崩溃恢复、bug、purge 事故）都可通过 `rebuild_refcount()`（全表扫描 changes → 重建计数 → 修正 gc_queue）自愈，不需要人工修库。
3. **GC 最终复查必须排除 pending_commits**：一个 blob 可能 refcount=0 但正被某个 5 分钟内未过期的 prepare（`pending_commits.need_blobs`）等待上传。物理删除前做最终检查：该 blob 被 `pending_commits`（未过期）引用 → 跳过本轮；purge 引发的队列项可立即删（无 prepare 关联）。复查在 GC 事务内完成。
4. **宽限期可撤销**：`gc_queue` 到期前，任何提交重新引用该 blob 时出队（提交事务内 `DELETE FROM gc_queue WHERE blob_hash=?`）。
5. **调度**：后台任务按 `gc.schedule`（默认每天 03:00）扫描 `due_at <= now` 的队列项，逐个复查 → 删除磁盘文件 + `blobs` 行。删除是幂等的（文件不存在视为成功）。
6. **`rebuild_refcount()` 入口**：管理员接口 `POST /admin/maintenance/rebuild-refcount`；服务端启动时若检测到上次未正常退出（`gc_meta` 脏标记）也自动触发。

## 4. 权限系统（目录级）

### 4.1 规则模型

一条规则 = **(仓库, 目录前缀, 主体, 权限级别, 是否屏障)**。

- **目录前缀**：`''`（仓库根）/ `art` / `art/char`。按**路径段**匹配，不是字符串前缀——`art` 匹配 `art/a.psd` 但**不**匹配 `artist/a.psd`。
- **主体**：`user:<id>` / `group:<id>` / `everyone`。
- **级别**：`none`（显式拒绝）< `read` < `write` < `admin`。
- **屏障（inherit=false）**：命中即终止向上回溯（详见下）。

### 4.2 解析算法（v0.4：inherit = 继承屏障）

**术语定死**：`inherit=false` 的含义不是"只控制本目录"，而是**该目录是一条继承屏障（barrier）**——当用户对**恰好该前缀**没有任何匹配规则时，屏障阻止继续向父目录回溯，直接得到 `none`。屏障的检查**与用户是否在该目录命中规则无关**（规则不存在 ≠ 屏障不存在）。

```
effective_level(repo, path, user):
    if user.is_admin: return ADMIN                       # 系统管理员穿透一切
    segs = split(path, '/')
    for depth in (len(segs) .. 0):                       # 从最具体到最泛
        prefix = join(segs[0..depth])
        rules = ACL[repo].prefix == prefix               # 该目录下的所有规则
        hit  = pick(rules, user)                         # 见下
        if hit is not None:
            return hit.level                             # 先命中先返回
            # 自下而上命中即返回 = 就近覆盖；
            # 注意此处不检查 inherit —— 屏障只在"未命中"时才起作用
        if has_barrier(rules):                           # 该目录存在任一 inherit=false 的规则
            return NONE                                  # 未命中用户规则 + 遇到屏障 → 拒绝
    return NONE                                          # 默认拒绝（fail-closed）
```

注意两个细节：

1. **屏障目录自身的行为**：如果用户在屏障目录**有**命中规则，返回该规则级别（屏障规则本身也参与 pick）；如果没有命中规则，屏障生效返回 `none`。也就是说，屏障 = "这个目录的权限只由它自己的规则决定，父级无权过问"。
2. **屏障规则未必是拒绝**：`inherit=false` 可以和任意 level 组合。例如 `art/internal` 上一条 `group:dev / write / inherit=false`，意味着 dev 组可写，而其他人在此目录全部失效（即使父目录给了 read）。

pick(rules, user) 不变：

```
pick(rules, user):
    candidates = []
    for r in rules:
        if r.subject == everyone: candidates.push((rank=0, r))
        if r.subject == user:     candidates.push((rank=2, r))
        if r.subject in user.groups: candidates.push((rank=1, r))
    sort by (rank DESC, level ASC)                        # 主体越具体越优先；同级时拒绝优先
    return candidates[0] or None
```

**语义要点**

1. **就近覆盖**：从最深的目录往上找，第一个有规则且匹配用户的目录生效。因此给 `art/secret` 单独配置即可覆盖 `art` 的授权，无需冗余配置。
2. **主体优先级**：同一目录下，针对"某个用户"的规则 > "用户所在组" > "所有人"。所以可以给全组 read，再单独给某人 none。
3. **拒绝优先**：同一优先级下 `none` 胜过 `read`（显式拒绝 > 隐式允许），避免"组授权把个人封禁覆盖掉"。
4. **默认拒绝**：任何路径没有命中规则且未遇屏障即无权限。仓库创建时自动写入一条 `'' + everyone + read` 作为基线（可在管理页删除）。
5. **屏障（v0.4 语义）**：`inherit=false` = 继承屏障。场景："给 `art` 开 read，但 `art/internal` 完全独立、父级规则管不到它"——在 `art/internal` 上建一条 `inherit=false` 规则（level 按需，比如给组 dev write）即可。该目录之外的一切照旧；该目录内的解析永远终止于 `art/internal` 自己的规则表。

### 4.3 权限 → 操作矩阵

| 操作 | 最低权限 | 校验点 |
|---|---|---|
| 查看仓库信息 / 列目录 / 下载文件 | `read` | `tree`、`blobs GET` |
| 查历史 / diff | `read` | `log`、`diff` |
| 提交（新增/修改/删除路径） | `write`（**逐路径校验**） | `commit/prepare` |
| 加锁 / 解锁 | `write` | `locks POST/DELETE` |
| 查看他人锁列表 | `read` | `locks GET` |
| 强制解锁（强制解锁） | `admin`（本目录） | `locks DELETE ?break=true` |
| 清除文件/目录及其历史（purge） | `admin`（本目录）**且**系统管理员，需二次确认 | `/admin/repos/{repo}/purge` |
| 配置目录权限 | `admin`（本目录） | `admin acl` |
| 修改仓库设置 / 删除仓库 | 系统管理员 | `admin repos` |
| GC / 存储统计 | 系统管理员 | `admin maintenance` |

**逐路径校验**是关键：一次提交可能涉及多个目录，服务端对**每一个变更路径**独立求 `effective_level`，任一不满足即整单拒绝并返回具体哪条路径越权。

**读路径要"过滤"而不只是"校验"**（M2 实现澄清，2026-09-14）：`tree` 展开子目录时逐条按 `read` 过滤掉无权条目；`changes` 增量按行过滤，越权路径的变更**不得出现在响应里**；`GET /repos` 列表剔除本人对根没有 `read` 的仓库。只读校验请求前缀会漏掉"前缀有权限、子条目没权限"的情况。

**下载的授权对象是"路径"而不是 blob**（M2 实现澄清，2026-09-14）：blob 按 sha256 内容寻址、全局去重，同一份内容可能被多个路径引用。`GET /blobs/{hash}` 因此反查"哪些路径引用了该 blob"（`head_entries ∪ changes`，走 `idx_head_entries_blob`），**只要存在任一本人可读的路径即放行**；全部不可读 → 403，一个引用都没有 → 404。为避免该反查成为热路径瓶颈，迁移 004 补了 `idx_head_entries_blob(repo_id, blob_hash)`。

## 5. 锁定与并发编辑

### 5.1 锁模型

> **v0.4.17 收敛**：只剩**文件锁**。`dir` 锁（递归覆盖子树的目录锁）整体移除，理由是它带来的
> 复杂度远超收益：互斥判定要沿祖先链双向求交、强制解锁要连带释放子树、加锁后对新文件"自动生效"
> 又是一条隐式语义；而客户端实际需要的是"把我这次要改的几个文件锁上"。

- **粒度**：仅文件锁（`locks.path` 恒为文件路径，服务端拒绝目录路径）。
- **批量加锁**：客户端"锁选中的 N 项"展开为 N 次加锁请求（并发受限、部分失败可见）。语义收窄是**有意**的——锁的作用域是"加锁那一刻存在的文件"，此后新增的文件不在任何锁的保护下，用户对它们重新加锁即可。
- **状态**：`(repo, path) → { owner, token, comment, created_at, expires_at }`，`UNIQUE(repo,path)` 保证同一路径只有一把锁。
- **互斥规则**：同一路径已被**他人**持有的**有效**锁占用 → 拒绝并返回冲突详情（谁持锁、何时加锁、备注）。同一路径被**本人**持锁 → **幂等**返回既有锁（重开客户端重复加锁不报错）。
- **持有**：客户端 `POST /locks` 拿到 `token` 并写入工作副本 `wc.db` 的 `locks` 表，后续提交凭 token 证明所有权。
- **释放**：显式 `DELETE`；带 `?break=true` 需该文件所在目录的 `admin` 权限且 **reason 必填**（记审计，§5.5）。
- **过期**：`expires_at` 可选（管理页可配默认 TTL，如 7 天）；**过期即失效**——有效性判定只看 `expires_at`，过期锁不阻塞任何人，行由惰性清理回收。生命周期治理（续期、孤儿锁、启动对账）见 §5.5。

### 5.2 锁策略：先锁后提交（唯一语义）

仓库级 `lock_policy` / `needs_lock` 两个字段**已废弃**（列保留、恒写 `strict` / `''`，建仓与仓库设置都不再让用户选）：

| 维度 | v0.4.17 |
|---|---|
| 谁需要持锁 | **每一个变更路径**（新增 / 修改 / 删除的文件）都必须是**本人**持有效锁 |
| 不满足时 | `commit/prepare` 返回 `412 NEEDS_LOCK` + **未持锁路径清单**（客户端据此自动补锁或提示） |
| 被他人持锁时 | 同样拒绝，冲突详情带 `owner` / `lock_path`（不再区分"advisory 放行"） |
| 目录条目 | 不参与锁校验（目录不进 `changes`，由服务端 `ensure_dirs` 隐式补建） |

**锁所有权判定**（提交校验与权限判定统一使用）：对每个变更路径 `p`，**单点查** `locks(repo_id, p)` 走 `idx_locks_path`，命中且 `owner_id = 当前用户` 且未过期 ⇒ 持锁成立。原先的"沿祖先链查 dir 锁"（最多 N 层点查）随 dir 锁一并删除。

**客户端配套（§6.5）**：勾选即提交的体验由"**自动补锁**"保证 —— 服务端回 `412 NEEDS_LOCK` 时，客户端按返回的路径清单逐个补锁并重试一次 `prepare`；任一加锁失败（他人持锁）则原样抛出并点名持有者，用户可选择排障或改选其他文件。**提交成功后自动释放本次提交文件上本人持有的锁**（含此前手动加的）。锁入口只有**一个**：工作副本目录树上右键节点 → 加锁 / 解锁 / 强制解锁（**独立"锁"视图已删除**，工具栏也不再放一份按钮，见 §6.5）。

### 5.3 提交流程（两阶段，v0.4：commit_id 幂等）

客户端为**每次提交尝试**生成一个 UUID `commit_id`，在 prepare 与 commit 中都携带。两个凭据职责分离：

- **`commit_id`**（客户端生成）：幂等键。网络重试/超时后重发 commit，服务端依据 `commits` 表返回同一结果，**绝不产生重复修订**。
- **`commit_token`**（服务端签发，5 分钟）：安全凭据，绑定 `user / repo / commit_id / base_rev / changes_hash`，防止 prepare 与 commit 之间变更清单被篡改或挪用。

**阶段一 `commit/prepare`** — 所有校验在此完成，失败不产生任何副作用：

1. 校验 `base_rev == repo.head_rev`？不等 → 返回 `409 OUT_OF_DATE` + 冲突路径列表（客户端提示先 update）。v1 保持**严格相等**（不做"旧 base 可提交"的宽容语义，避免路径冲突判定复杂化）。
2. 若 `commit_id` 已存在于 `commits` 表 → 直接返回该次提交的 `{rev, ...}`（幂等短路）。
3. 逐路径 ACL 校验（§4.3）。
4. 逐路径锁校验（§5.2）：每个变更路径必须由**本人**持有有效锁，未持锁的路径汇总成一条 `412 NEEDS_LOCK`（带路径清单）返回。
5. 路径合法性（§6.6）：拒绝 `..`、绝对路径、反斜杠、`\0`、超长（段 >255B / 全路径 >1024B）、`.b-artifact` 保留名、Windows 保留名与非法字符（`400 INVALID_PATH`）；非 NFC 路径返回 `400 PATH_NOT_NORMALIZED`。
6. 收集缺失 blob，落 `pending_commits` 行，返回 `{ need_blobs: [...], commit_token, commit_id, expires_in }`。

**阶段二 `commit`**：

1. 校验 `commit_token` 未过期、`user/repo/commit_id/base_rev/changes_hash` 五元组与 token 绑定一致。
2. 幂等检查：`commit_id` 已在 `commits` 表 → 返回既有 `{rev}`，不再落库。
3. 校验所有 blob 已就位且 sha256 正确。
4. **单事务**：`UPDATE repos SET head_rev=head_rev+1 WHERE id=? AND head_rev=?`（乐观锁，`changes` 为零则回滚）→ 插入 `changes` 行 → 更新 `head_entries`（目录 Tombstone 物理删除子树行）→ `commits` 插入幂等记录 → `blobs.refcount += 1`（并入队删除 gc_queue 中的复活项）→ 写 `revisions` → 删除对应 `pending_commits` → 写审计。
5. 返回 `{ rev: N }`；`manifest_hash` 由后台异步补算（§3.3）。

**失败语义**：commit 返回网络错误时客户端**原样重试同一 commit_id**——可能服务端其实已成功，幂等检查会返回相同 rev。若 prepare 过期（>5 分钟）则需重新 prepare（新 token，同一 commit_id 不变，幂等键不换）。

### 5.4 客户端更新（update）时的冲突

因为是"先锁后改"，正常流程冲突极少。**v0.4.17 之后**所有变更都要求本人持锁，但 update
仍会撞上"本地已改却没持锁"的情形（用户在加锁之前就动了文件，或在锁过期后继续改），所以
下面这套处理照旧必须保留：

- 文件本地未改 → 直接覆盖。
- 本地已改 & 服务器也改了：
  - 本地即为**锁持有者** → 保留本地内容，标记 `needs-commit`，**不覆盖**。
  - 否则 → 服务器版本落到工作文件，本地版本另存 `<file>.mine`，服务器旧基线存 `<file>.r<base>`，标记 `conflicted`。
- **绝不删除任何一方内容**。冲突解决由用户在客户端选择保留哪份。

### 5.5 锁的生命周期治理（孤儿锁、续期、过期）

**状态模型**：锁行含 `expires_at`，**有效性判定 = `expires_at IS NULL OR expires_at > now()`**。过期锁不立即删除（行保留，惰性清理），但一切"是否持锁"判定（§5.2、`POST /locks` 互斥检查）只看有效锁——过期即失效，无需任何管理动作。

**TTL 与自动续期**：

- 仓库级配置默认 TTL（默认 7 天，可设"永不过期"）。
- 客户端**工作副本打开期间**（Electron 主进程存活）对本人持有的锁每 10 分钟心跳续期（`POST /locks/refresh`，携带 token）；客户端关闭后停止续期，锁在 TTL 到期后自然失效。
- 续期采用"绝对到期时间"（服务端返回新的 `expires_at`），避免客户端时钟漂移问题。
- 心跳失败不弹窗打扰：连续 3 次失败后在 UI 角标提示"锁可能已过期"，用户提交前会重新校验。

**孤儿锁的三个来源与处理**：

| 来源 | 表现 | 处理 |
|---|---|---|
| 客户端崩溃 / 断电 | 锁仍在 TTL 内 | 用户重开工作副本后客户端自动续期，无需干预 |
| 长期离线 / 离职 | 锁过期后未续 | TTL 自然失效（默认 7 天）。**v0.4.17 后代价更明确**：由于所有变更都要求本人持锁，过期锁意味着该用户必须先重新加锁才能提交（不再是"advisory 下仅仅阻塞他人"） |
| 工作副本被整目录删除 | 本人已无 wc.db，锁仍在 | 用户在**任意**工作副本或管理页"我的锁"里释放；或等 TTL 过期 |

**本人锁的跨副本管理**：`GET /repos/{repo}/locks?owner=me` 列出本人在该仓库的全部有效锁（服务端记录为准，不依赖任何本地 wc.db），支持逐个或批量释放。这保证"副本删了锁还在"永远有出口。

> **术语映射（v0.4.17 起）**：界面上统称**「强制解锁」**（本文档全文同此）；底层标识仍是 `break` —— API `DELETE /locks/{path}?break=true`、审计动作 `lock.break`、数据库列 `broken_at` / `broken_by` / `break_reason`、CLI `--break`、服务端函数 `break_lock`。改的是**用户看到的词**，不改协议与历史数据。

**强制解锁（break）语义强化**：

- 强制解锁 = `DELETE /locks/{path}?break=true`，需目录 `admin` 权限，**必须填 reason**（审计必填字段）。v0.4.17 后锁只剩文件级，权限作用域是该文件**所在目录**，且不再有"破一把目录锁连带释放整棵子树"的情形——一次强制解锁只影响一个路径。
- 强制解锁后锁记录保留（`broken_at`、`break_reason`、`break_by`），供历史查询；被强制解锁的用户下次打开工作副本时客户端对账发现锁已不属于自己，清理本地记录并在 UI 提示。
- v1 不做强制解锁通知推送；管理页锁列表按 `最近被强制解锁` 排序可查。

**客户端启动对账**（`wc.db locks` 表 vs 服务端）：

1. 本地记录的锁逐个 `GET /locks?path=` 核对：服务端无此锁 / owner 非本人 / 已过期 → 清理本地行 + UI 提示；
2. 服务端有效但本地缺失 → 拉回本地（重新登记 token）；
3. 对账在后台执行，不阻塞 UI。

## 6. 客户端设计（Electron）

### 6.1 工作副本布局

```
<检出目录>/
├─ .b-artifact/                        # 元数据（不参与版本管理）
│  ├─ wc.db                      # SQLite（v0.4：替代 entries.jsonl）
│  │    ├─ meta                  # { server, repo, root_url, revision, sparse_paths[], user }
│  │    ├─ entries               # path PK, kind, base_rev, base_hash, size, mtime, mode, status
│  │    ├─ pending               # 待提交集：add/modify/delete 暂存
│  │    └─ locks                 # 本人持有的锁与 token
│  ├─ pristine/                  # 基线内容（硬链接到全局缓存）
│  │  └─ 3f/a1/3fa1c8...
│  └─ wc.lock                    # 进程级排他锁，防两个客户端实例同开一个副本
├─ characters/                   # 版本管理的文件（部分检出仅含选中子树）
└─ README.md
```

**pristine 存储**：与 SVN 的 `.svn/pristine` 同思路，保存"当前基线版本"的字节副本。它带来三个能力：

1. **离线三态对比**：`本地 vs 基线` 无需网络即可算状态、出 diff、还原（revert）。
2. **本地合并**：文本文件可用 `BASE / MINE / THEIRS` 做三方合并。
3. **不依赖 mtime**：以内容哈希判定是否修改（mtime 只作为快速跳过扫描的启发式）。

**磁盘优化**：pristine 默认用**硬链接**指向全局缓存 `~/.b-artifact/cache/<hash>`（同一文件在多个工作副本/多个修订间只占一份物理空间）。文件系统不支持硬链接时自动降级为复制。

### 6.2 文件状态机

| 状态 | 判定 |
|---|---|
| `unversioned` | 存在于工作副本，不在 `entries` 中，且未被 ignore |
| `ignored` | 匹配 `.b-artifactignore`（gitignore 语法）。**按工作副本/仓库生效**：规则文件就在副本根目录，可随其他文件一起提交共享（v0.4.19 起**没有**全局追加规则 —— 每个仓库要忽略的东西不一样，放公共配置必然互相打扰） |
| `normal` | 文件哈希 == 基线哈希 |
| `modified` | 文件哈希 ≠ 基线哈希，且基线存在 |
| `added` | 有文件无基线，且已 `add` 到待提交集 |
| `deleted` | 有基线无文件（或已 `delete`） |
| `missing` | 文件被外部删除，尚未标记 |
| `conflicted` | 存在 `.mine` 伴生文件 |
| `needs-update` | 服务器该路径 `changed_rev > base_rev`（由 update 扫描得出） |
| `locked-by-me` / `locked-by-other` | 查锁表 |
| `out-of-date` | 工作副本 `revision < server.head_rev` |

状态计算：`scan(root, sparse_paths, ignore) → entries` 与 `wc.entries` 做集合运算，配合 pristine 哈希比对。

> **实现澄清（2026-09-15，M4 落地时对齐）**：上表其实混了**三个不同的轴**，实现里要分开看：
>
> - **逐条状态（9 个）**：`unversioned` / `ignored` / `normal` / `modified` / `added` /
>   `deleted` / `missing` / `conflicted` / `needs-update`。这是 `StatusItem.status` 的取值域
>   （`core/scan.ts` 的 `StatusCode`），`shared/dto.ts` 与之逐字段对齐，由
>   `tests/dto-parity.test.ts` 双向赋值守住。
> - **锁轴**：`locked-by-me` / `locked-by-other` 不是条目状态，而是查锁表得到的**独立维度**
>   （一个文件可以同时是 `modified` 且被他人锁定）。界面上单独呈现锁列表，不并进状态列。
> - **工作副本级**：`out-of-date`（`revision < head_rev`）是**整个副本**的判定，落成提交时的
>   错误码 `OUT_OF_DATE`（§7.1）而不是逐条状态——因为用户要做的动作是"先 update"，不是"处理某个文件"。
>
> 界面侧还有一层**可勾选**判定（`isActionable` = 本地变更 ∪ `unversioned`），它比"可提交"
> （`isCommittable` = 本地变更 − `conflicted`）更宽：`unversioned` 必须先能勾上，
> 才谈得上"标记新增"。
>
> **已知边界（racy，2026-09-15 记录）**：快速路径是"mtime + size 都没变 ⇒ 内容没变"，
> 所以**在基线记录后的同一毫秒内**把文件改成长度相同的内容，会被判成未改动
> （与 git 的 racy-clean 是同一类问题；git 用 index 时间戳兜，我们没存那个时间）。
> 手动操作不可能命中，但**脚本化写入**可能。需要确定答案时走 `status({ forceHash: true })`
> ——界面上的"刷新状态"按钮用的就是这条。该边界有专门用例钉住（`tests/wc.test.ts`
> 的"状态判定的 racy 边界"）。
>
> **`conflicted` 的实现补充（2026-09-15）**：冲突不只是把状态标成 `conflicted`。撞冲突时
> 工作文件被换成服务端版本、`entry.base_hash` 跟着被覆盖，**共同祖先就丢了**——所以
> wc.db 迁移 v2 单独建 `conflicts` 表记录 base / theirs / mine 三方哈希与成因
> （`both-modified` 或 `deleted-remotely`）。详见 §6.5 的实现澄清。

### 6.3 关键流程

**检出（checkout，支持部分检出）**
```
1. GET /repos/{repo}/info            → head_rev, 默认策略
2. 用户勾选目录树（可多选前缀）
3. GET /repos/{repo}/tree?rev=head&prefix=<p>   （每个前缀一次）
   → 过滤出该用户有 read 权限的条目
4. 汇总所需 blob hash → 与本地缓存求差 → 并发下载缺失（信号量限 4~8 并发）
5. 写文件到工作副本 + 建立 pristine 硬链接 + 写 wc.db（meta/entries）
```

**更新（update）**
```
1. GET /repos/{repo}/changes?from=base_rev&to=head_rev&prefix=<sparse>
   → 只有变化路径，通常几十条而非全量清单
2. 比对本地状态，分类处理（覆盖 / 冲突 / 删除）
3. 下载缺失 blob → 更新工作文件与 pristine
4. 写回 revision = head_rev
```

**提交（commit）**
```
1. 扫描 + 状态计算 → 变更集（用户可勾选）
2. 对每个 add/modify 计算 sha256（并行，跳过 mtime+size 未变的文件）
3. POST /commit/prepare  → 拿 need_blobs[] 与 commit_token
4. 并发上传缺失 blob（PUT /blobs/{hash}，原始二进制流，带进度）
5. POST /commit          → rev N
6. 更新 entries 基线 = N，清理待提交集
```

**M4 实现澄清（2026-09-14，均由冒烟/单测暴露后定案）**：

0. **`remove` 要区分"已纳管 / 只是 add / 完全陌生"**（v0.4.19）：
   有基线条目 → 记一条待删除；只在待提交集里（`add` 过）→ **撤销那条 add**；
   完全陌生（未纳管的新文件）→ 什么都不记，删掉文件即可。
   旧实现一律 `stage('delete')`：删一个刚建的新文件会给服务端发一条"删除一个它从没见过的
   路径"，提交里平白多出一条变更（树上直接删除的入口上来之后暴露得很明显）。
1. **`add` 连带纳入祖先目录**（svn 语义）。`add a/b/hero.psd` 时，若 `a`、`a/b` 尚
   无基线条目，一并 stage 为 `added`（但**不进 changes**——服务端 `ensure_dirs` 会自补，
   提交目录行只会换来重复条目）。否则提交后这两个目录仍显示 `unversioned`，用户会反复
   add 出重复目录。与 update 端的 `ensureAncestorEntries` 对称：服务端的 changes 流只
   携带显式变更行，隐式祖先目录只写 `head_entries`，客户端必须自己补登记。
2. **空目录不单独入库**。只 `add` 一个空目录就 commit 时，change 清单会是空的——空目录
   在服务端没有独立实体。此时直接抛 `NO_CHANGES`（"请先放入文件"），而不是把空请求发给
   服务端换一句看不懂的报错。
3. **强制解锁要求对该目录有 admin 权限**。`write` 只能解自己持有的锁；他人的锁无论是否带
   `--break` 都报 `PERMISSION_DENIED`（403）。所以"解锁失败"要分三种情况看：锁不存在
   （`NOT_FOUND`）、不是自己的锁（`PERMISSION_DENIED`）、强制解锁但权限不够（`PERMISSION_DENIED`
   + 提示需要 admin）。

**安全基线**：`contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`；preload 只暴露形如 `invoke('wc:commit', payload)` 的窄接口，主进程侧做参数校验；渲染层不接触 token（token 存主进程 + `safeStorage` 加密）。

**把引擎放在主进程的理由**：大文件哈希、并发传输、增量扫描会长时间占 CPU/IO，放主进程可用 worker_threads 并行；渲染层只做展示，避免 UI 卡顿。

**打包（M4 交付物，2026-09-15）**

- **asar 只装 `dist/` 与 `package.json`**。渲染层已由 Vite 预打包，主进程只依赖 `electron`
  与 Node 内置模块——**运行时不从 `node_modules` 取任何东西**。所以 `client/package.json`
  的 `dependencies` 是**空的**，Vue / Element Plus / Pinia 这些全部归 `devDependencies`。
  这一条把 asar 从 36 MB 压到 1.5 MB。将来真加了运行时依赖，`files: ['!node_modules/**']`
  会让它缺席，而**打包产物冒烟会立刻暴露**（这正是那道门禁存在的意义）。
- **`electronDist` 指向本地分发**。`node_modules/electron/dist` 就是官方 zip 的解压结果，
  指过去就免掉每次联网下载 ~100 MB（沙箱里这一步要几分钟，而且可能反复重下）。
- **打包产物必须自己跑一遍冒烟**。asar 改变文件布局，`preload` 路径、
  渲染层的相对资源路径（`base: './'`）、由 `__dirname` 推导的 `CLIENT_ROOT` 都可能在打包后失效。
  `scripts/m4_package.sh` 把"构建 → 打包 → 用打包产物跑同一套 143 项断言"串成一条链路。
- **dmg 在本沙箱做不出来**：需要额外下载 dmgbuild 工具包，而
  `electron-userland/electron-builder-binaries` 这个 host 完全不可达（curl 直接返回 000）。
  默认只出 **zip**（macOS 上是合法的分发形态，也是 autoUpdater 消费的格式）；
  要 dmg 就在联网环境把 `mac.target` 改成 `[dmg, zip]`。
- **未做代码签名与公证**：沙箱里没有 Developer ID 证书（`0 valid identities found`），
  产物在本机可直接运行；对外分发需要签名 + 公证，否则 Gatekeeper 会拦。

**M4 第三阶段实现澄清（2026-09-15，全部由 Electron 冒烟暴露后定案）**：

1. **IPC 载荷必须是可结构化克隆的纯数据**。Vue 的 `ref([...])` 取出来是响应式 Proxy，
   直接丢给 `ipcRenderer.invoke` 会被 Chromium 拒掉，**错误信息只有一句 "An object could
   not be cloned."**，没有通道名也没有参数名。修法：`renderer/api.ts` 的 `call()` 统一做一次
   JSON 归一化（载荷本来就全是 JSON 形状，主进程侧还有 schema 兜底）。
   回归测试直接拿 `structuredClone()` 断言可克隆性——那正是 Electron 的约束。
2. **同一个工作副本实例重复 `adopt` 不能 close**。提交/更新之后要把前进的 rev 同步给顶栏，
   于是拿当前实例再 adopt 一次；无条件 `close()` 等于把自己关掉，后续所有操作都撞
   `database is not open` / `statement has been finalized`。现在先比实例再决定关不关。
3. **状态表里"可勾选"≠"可提交"**。`unversioned` 不在提交集里，但必须能勾选——否则
   "标记新增"永远点不动，用户根本无法把新文件纳入版本控制。拆成两个判定：
   `isActionable`（可勾选：本地变更 ∪ unversioned）与 `isCommittable`（会被提交：本地变更 − conflicted）。
4. **Element Plus 的 CSS 必须显式 import**。`import ElementPlus from 'element-plus'` 只带组件
   不带样式；漏掉 `element-plus/dist/index.css` 时界面能跑、逻辑全对，但完全没有样式
   （图标撑成巨大的黑色色块）。**组件级单测发现不了**（el-* 全被替身掉了），只有真实浏览器
   截图能看出来——这是本项目第二次"靠看截图抓到假绿"。
5. **宿主可能注入 `ELECTRON_RUN_AS_NODE=1`**（WorkBuddy 自身就是 Electron 应用）。带上它，
   Electron 二进制会退化成纯 Node：`--version` 打出 Node 版本、窗口永不出现。所有启动入口
   （`scripts/start.mjs`、冒烟脚本）都必须先 `delete env.ELECTRON_RUN_AS_NODE`。
6. **preload 必须是 CommonJS**。`sandbox: true` 不支持 ESM preload，所以构建产物是
   `dist/preload/index.cjs`（esbuild 单独出一份 CJS），主进程则是 ESM。
7. **渲染层 `base: './'`**。Electron 以 `file://` 加载 `index.html`，用默认的 `/` 会让资源
   指向 `file:///assets/...` 直接白屏。同时 `index.html` 里下了严格的 CSP
   （`connect-src` 只留 dev server 的 websocket——渲染层本来就不该访问网络，一切走 IPC）。

**M4.8 需求变更轮：工作副本交互重做（v0.4.17）**

1. **状态呈现改为目录树，不是"树形化的表格"**。数据来源不变（仍是一次全量 `status` 扫描的
   `StatusItem[]`），只是换成按路径前缀聚合的树：目录节点汇总"变更 N"、文件节点带状态标签与
   锁标记。**默认只展开含变更的分支**——工作副本动辄上万文件，全展开既没意义也会卡住渲染；
   另给"只看变更"开关。平铺的 `StatusTable` 退化为"只看变更"时的可选视图（保留，便于按状态排序）。
2. **「刷新状态」按钮删除，改为自动同步**。主进程 `fs.watch(root, { recursive: true })` 递归监听
   工作副本根，事件 300ms 防抖后重算状态并推送渲染层。三条实现约束：
   - **忽略 `.b-artifact/` 与忽略规则命中的路径**，否则 wc.db 自己的写入会自触发成死循环；
   - **自写入抑制窗口内的事件必须"推迟"，不能"丢弃"**（v0.4.19 修）：应用自己的写盘
     （删除 / 还原 / 保存忽略规则）会在监听上开一个 1.5s 的抑制窗口，而**用户完全可能在这
     1.5s 内改别的文件**。旧实现直接 `return` 丢掉那个事件 —— 那次变化就**永远**不反映到
     界面上。现在改为"推迟到窗口结束再算一次"：最坏多扫一次，但不会漏（E2E 用"保存忽略规则
     后 0.5s 改写 readme.txt"稳定复现过）；
   - **自己写入的文件要抑制**（update / revert / 检出落盘）：这些操作本来就会刷新状态，
     再触发一轮 watcher 只是浪费；用"写入窗口"内的路径集合过滤；
   - **监听失败要降级**：超大目录树或平台差异（Windows 上 `recursive` 由 Node 模拟、
     规模大时资源占用显著）导致 `fs.watch` 不可用时，回退为"打开/提交/更新后刷新 + 顶栏
     一个不显眼的刷新按钮"，**不能让状态停在过期视图上**。
3. **「标记新增」按钮删除，但"默认不勾选"**。未纳管文件在树里显示为「新增」并计入变更总数，
   但**不进入默认提交集**——自动把工作副本里所有陌生文件都提交上去太危险（构建产物、
   临时文件、素材软件的中间文件），必须由用户勾选确认。忽略规则（每副本的 `.b-artifactignore`，
   设置里的追加规则）仍是唯一的"排除"手段。
4. **提交说明可空**。服务端 `message` 本就是 `Option<String>`（`api/commit.rs`），是客户端
   多加了一道必填校验；改为"留空即以文件名摘要兜底"（仅在界面展示，不污染库里的 message）。
5. **删除 / 还原按"勾选集"，新建按"当前节点"** —— 两条轴分工要写死，不能混：
   - **勾选** = "对哪些东西动手"（提交集、删除集、还原集都看它）；
   - **当前节点** = "动作落在哪儿"（新建文件/目录的落点、右键加锁的目标）。
   删除曾经按"当前高亮那一行"执行：用户勾了三项、删除却只动了最后点过的那一行（真实反馈）。
   现在删除与还原都以勾选集为准，按钮上直接显示数量「删除（N）」，确认框写明"勾选的 N 项"；
   **删除后保留勾选**（删除只是记为待删除，要提交才生效，勾着正好提示下一步）。
6. **刚打开工作副本时树上是干净的**：**不预勾选任何项**，也没有高亮的"当前节点"
   （真实反馈："刚打开工作副本时，目录树都不应该选中"）。原先按"全部本地变更"预勾选，
   结果是打开就一片勾选，而且 `el-tree` 在子项全勾时会把**父目录**也带成勾选态 ——
   看起来就像"目录被选中了"。清空之后"勾选即提交"依然成立：**用户从未动过勾选时，
   提交集 = 全部本地变更**（提交按钮照常显示数量，提示条写明"未勾选时提交全部变更"）；
   用户一旦自己动过，就以他的勾选为准（把勾全清空 = 什么都不提交）。
7. **勾选即提交，靠"自动补锁"落地**。§5.2 要求每个变更路径都由本人持锁，而用户的心智是
   "勾上 → 提交"。所以提交流程是：`status` → 对所选路径中未持锁的批量 `POST /locks`
   （**逐个**，任一失败即中止并列出被他人持锁的路径）→ `commit`。加锁与提交合并在一次点击里，
   但**两个动作在界面上可见**（进度与失败原因分开提示），否则用户无法解释"为什么提交没动"。
6. **树上直接增删**（**新建文件已去掉**，见下）。新增 IPC：`wc:mkdir`（建目录）、
   `wc:delete`（**本地删除 + 记 pending delete**，目录递归；删的是工作副本里的文件，但基线在
   wc.db 里、`revert` 可恢复，所以不需要进系统回收站——**这一点必须在确认框里说清**，
   否则用户会以为文件被永久删除）。删除目录时其下每个文件都是独立变更路径，
   各自都要持锁（§5.2），因此删除大目录前会先做一次批量加锁。
   **v0.4.19 去掉「新建文件」**（真实反馈："去掉新建文件功能"）：资产文件由用户的创作工具
   产生，版本工具里"新建一个空文件"没有意义。删得很彻底——按钮、`wc:writeFile` 通道、
   渲染层 `api.writeFile`、`store.createFile`、引擎 `createFile` 与 `EXISTS` 错误码一并移除
   （不留死代码，也少一个 IPC 面）；**「新建目录」保留**：空目录是组织结构，需要它。改规则的弹窗**可拖动**（`el-dialog` 的
   `draggable`）—— 它会挡住后面的目录树，用户得能把它拖开；「打开已有副本」弹窗同理。
7. **加锁入口只有一个（工作副本目录树的快捷菜单），锁视图整体删除**。独立的「锁」页签连同
   `LocksView.vue` 一并删除；加锁 / 解锁 / 强制解锁**只在节点右键菜单里**（工具栏那一行不再
   重复放一份 —— 真实反馈："上面的一行菜单"太挤，锁是低频动作）。实现约束：
   - **动作目标必须一直可见**：工具栏显示「当前：<path>」。这条是被真实反馈逼出来的 ——
     Element Plus 的**复选框带 `@click.stop`**，点它**不会**更新"当前节点"，于是"用复选框
     选中一个目录、再点加锁"实际作用在**上一次点过的那个文件**上（用户的描述是"选中目录
     却锁了某个文件，而且无法解锁"）。现在改用 `@node-click` 设当前节点，并且**去掉了
     `check-on-click-node`**：勾选是"提交选择"、选中是"操作目标"，两件事不再互相串。
   - **目录上的动作按整棵子树生效**（§5.1"批量加锁由客户端展开为 N 个文件锁"）：
     加锁 = 对子树内每个**未持锁的文件**逐个加锁；解锁 = 解子树内**我的**锁；
     强制解锁 = 破子树内**他人**的锁（reason 必填）。批量结果如实报"成功 N 个、失败 M 个"
     并点名第一条原因，不因为个别失败就整批放弃。
   - **目录节点聚合显示子树锁数**（「已锁 N」/「他人锁 N」）：前者告诉用户"我该去哪儿解锁"，
     后者解释"为什么我加不上锁"。菜单里的加锁项按"还能加锁的文件数"决定可用性与计数。
   - **加锁不弹备注框，点了就锁**：加锁是高频动作，每次都面对输入框太啰嗦。备注字段在协议
     与数据模型里都还在（CLI `-m`、管理端仍可见），只是客户端这个入口不再采集。
   - **提交后自动解锁**：提交成功后，**本次提交涉及的文件上、由本人持有的锁全部释放**
     （不论是提交时自动补的还是此前手动加的）。文件已经交上去了，锁就该交还 —— 否则下一个
     想改这个文件的人要等 TTL（默认 7 天）。只动"本次提交的路径"，锁着但没提交的不受影响。
   - **三种手势显式写死**（不依赖 Element Plus 的默认值）：点**标签**=只选中、点**复选框**=勾选、
     **双击目录**=展开/收起。⚠️ `checkOnClickLeaf` 的**默认值是 `true`** —— 只关
     `check-on-click-node` 并不够：那样点**文件**标签仍会悄悄切换它的勾选（目录因为"非叶子"
     才不受影响，行为不对称），提交集因此莫名变空（E2E 抓出来的真 bug）。
   - **我方操作成功后锁列表要"立刻本地生效"（乐观更新）**：界面上的锁标记完全依赖
     `GET /locks` 的结果，那次请求偶发失败（网络抖动 / 主进程忙）时，标记会停在过期状态 ——
     用户看到"锁已经解了、树上还显示已锁"，怎么点都不变。所以加锁 / 解锁成功后**先按本地
     已知事实改列表**，下一次成功的 `GET /locks` 再对账（`utils/locks.ts::applyLocalLocks`，
     纯函数、有单测）。界面的正确性因此不再取决于某一次请求的成败 —— 这条是被"同一套 E2E
     在打包产物上偶发红、源码树上全绿"逼出来的。
   - **窗口被遮挡时不能依赖浏览器的后台节流**：客户端靠后台定时器活着（15s 锁轮询、
     自动同步推送），而 Chromium 对隐藏窗口会把定时器节流（隐藏 5 分钟后降到一分钟一次）
     —— 窗口建出来时就显式 `backgroundThrottling: false`。E2E 也栽在这上面：窗口不可见时
     脚本从"变慢"到"看着像卡死"（真事故过）。
   - **锁状态要主动刷新**：锁是服务端状态，**别人加锁不会产生任何本地文件变化**，文件监听
     根本触发不到。所以工作副本打开期间每 **15s** 静默拉一次 `GET /locks`（一次索引范围查询），
     另外每次自动同步推送也顺手刷一遍。否则"同事刚锁了某个文件"要等到用户自己点一次操作
     才看得见——那正是"状态对不上、解不开"的观感来源。
   - **勾选与展开都必须"受控"，否则刷新会丢**：`el-tree` 的 `store.setData()` 在 `data`
     引用变化时会**清空 nodesMap 重建全部节点**（自动同步每推一次状态都会产生新数组），
     勾选/展开状态随之丢失，只按 `default-checked-keys` / `default-expanded-keys` 复原一遍。
     所以两者都由组件持有并**实时回灌**：勾选按"当前勾选集"回灌（**打开时为空**，
     用户勾什么就是什么；提交 / 还原后清空）；展开监听 `node-expand` / `node-collapse`
     跟住用户操作，新出现的**有变更**目录补一次展开（只补一次，用户手动折叠不会被顶开）。
     这两条是被真实反馈逼出来的：**刷新把用户勾好的项冲掉了**。
   - **当前节点是派生值**（按 `currentPath` 从当前树现查），不缓存节点对象 —— 树每次重建
     都是新对象，缓存下来就成了过期快照，工具栏的"可加锁 N / 已锁 N"会按旧数据算。
   - **双击目录 = 展开 / 收起**，单击只选中（`expand-on-click-node=false` 保持不变）。
     el-tree 没有 dblclick 事件，所以在自己的插槽内容上监听，再调节点实例的
     `expand()` / `collapse()`；展开箭头单击仍然可用。
   - **右键节点弹菜单**（`@node-contextmenu`）：加锁 / 解锁 / **强制解锁** —— 这是锁动作的
     **唯一入口**。右键即把该节点设为"当前节点"，菜单项的可用性/计数都按它算
     （`claimable` / `myLocks` / `otherLocks`）。菜单项按"当前能不能做"启用/禁用，
     点外部 / Esc / 滚动即关闭。
   - **术语**：界面上一律叫「**强制解锁**」（= 底层 `?break=true`，见 §5.5 的术语映射）；
     按钮 / 菜单 / 对话框 / 审计动作标签全部统一。
   - **菜单必须"点别处就关"，且必须监听捕获阶段**：`el-tree` 的节点内容与复选框都带
     `.stop`（`withModifiers(["stop"])` / `@click.stop`），冒泡阶段的 document 监听**收不到**
     树里的点击（用户的原话："左键点击目录树的其他位置时，右键菜单没有关闭"）。
     `mousedown` 与 `click` **两条捕获都要挂**：真实点击必有 `mousedown`，而键盘激活 /
     程序化 `.click()` 只发 `click`。判定"是否点在菜单内"再跳过，这样点菜单项不会被自己关掉。
   - **程序化展开/收起不带事件**：`Node.collapse()/expand()` 只是状态赋值，**不会**触发
     `node-collapse` / `node-expand`（只有点展开箭头那条路径才发）。所以双击展开/收起时
     必须**同时改自己的展开集合**，否则下一次数据重建会按 `default-expanded-keys` 把它又展开回来
     —— 表现就是"双击收起没反应"（真 bug，E2E 抓出来的）。
8. **打开已有副本**：工作副本页顶部与空态各一个入口，弹窗 = 最近打开（`config.recent`，
   逐条做存在性检查并剔除失效项）+ 浏览目录。打开失败（`NOT_A_WORKING_COPY`）时顺手把该条
   从最近列表里删掉——这是主进程 `wc:open` 已有的行为，界面只需如实呈现。
   - **弹窗里的"操作列"必须钉在右侧**（`fixed="right"`）：原先弹窗写死 620px，而四列最小宽度
     合计 660px，「打开」被挤进横向滚动区（用户的原话是"看不到，还需要拉滚动条"）。
     三层一起治：宽度改为 `min(92vw, 760px)` 自适应、列宽收紧 + 目录列 `show-overflow-tooltip`、
     操作列固定；再补一条**整行可点即打开**（`@row-click`），按钮只是备选。
   - **`config` 是快照，检出 / 打开之后要重拉**：主进程把记录写进 `config.recent`，而渲染层的
     `store.config` 只在登录时读过一次 —— 不重拉的话，刚检出完打开这个弹窗，最近列表甚至是
     空的（E2E 抓出来的真 bug）。现在 `checkout` / `openWorkingCopy` 成功后都会
     `refreshConfig()`（静默，不动 busy、不弹提示）。
   **仓库页的「检出」与「最近打开」成功后自动切到工作副本页**：用户点完这两处，下一步一定是
   在工作副本里干活，留在仓库页只会让他再点一次菜单（视图 `emit('goto', 'workspace')`，
   由 `App.vue` 统一切页）。

> **术语（v0.4.19 改名）**：svn/git 里的 *sparse checkout*，本项目界面上叫「**部分检出**」
> —— 直白说就是"只把勾选的目录拉到本地，其余留在服务端"。文档与本仓库的历史记录里
> 出现过旧名「稀疏检出」，两者完全同义（协议字段 `sparse_paths`、CLI 参数 `--sparse`
> 属于接口标识，不随界面改名）。

> **仓库级读操作一律由调用方显式给仓库**（v0.4.20）：`repo:log` / `repo:treeAt` /
> `repo:downloadRevision` 的 IPC 参数里都有必填的 `repo`。此前它们取"当前工作副本的仓库"，
> 于是**没打开副本时仓库页的目录树是空的**（真实反馈："工作副本打开后，仓库部分检出才能出来
> 目录树，不打开显示暂无数据"）。历史视图仍然坚持"你在哪个副本里就看哪个仓库的历史"——
> 但它现在**自己把副本的仓库传上去**，服务端不再猜。

**M4 第六轮实现澄清：目录树与勾选式部分检出（2026-09-15）**

1. **勾选语义要无歧义**。部分检出是白名单前缀，选择集必须"最小"：只要 `a` 在集合里，
   `a/b` 就是冗余的。所以 `normalizeSparse` 是唯一的不变量入口（去空去重 + 去掉被祖先覆盖的后代），
   勾选时**移除覆盖它的祖先**（用户在收窄范围）、同时去掉它的后代（放宽到整棵）。
   这样不会出现"勾了祖先之后再勾子目录，点了没反应"。
2. **只按需拉一层**。目录树用 `el-tree` 懒加载，展开哪层拉哪层（`tree?prefix=X&depth=1`），
   与历史视图同样的克制：大仓库上既省流量，也不去碰服务端的慢路径。
3. **"带权限标记"的落地方式是"看不到即无权限"**。服务端的 `tree` 已按 ACL 逐条过滤，
   所以界面上不存在"灰掉的目录"——看不见就是没读权限。树上方明确写出这句话，
   免得用户以为目录被漏掉了。
4. **换仓库必须清空勾选**。勾选的前缀属于上一个仓库，留着会拿着别的仓库的路径去检出
   （服务端会拒，但错误信息对用户毫无帮助）。

**M4 第五轮实现澄清：历史与设置（2026-09-15）**

1. **历史视图要主动避开服务端的慢路径**。`tree?rev=N`（非 HEAD 列目录）走的是
   `list_dir_at_rev`，M1.6 实测在 24 万文件档位 **7.4s**（唯一未达标核心项，§15.2）。
   所以界面上的用法是克制的：只在用户**选中某个修订**时按需拉**一层**（`depth=1`，
   且只拉该文件的父目录），不预取、不递归展开；并在非 HEAD 修订上给一条明示提示。
2. **清空 blob 缓存是安全的，前提是 pristine 是硬链接**。缓存是内容寻址的唯一物理副本，
   但每个工作副本的 `<wc>/.b-artifact/pristine/<hash>` 与它**硬链接**——删掉缓存里的名字只是
   链接数减一，pristine 依然可读，工作副本不会损坏。代价仅是下次需要重新下载。
   实现上**只删文件、保留目录骨架**，并跳过符号链接（免得跟到工作副本外面去）；
   这条语义有单测直接钉住（清缓存后 pristine 仍可读出原内容）。
3. **"下载此版本"不静默覆盖**。目标目录里已有同名文件时，落成 `<stem>.r<rev><ext>`，
   再冲突就加 ` (n)`。用户点"下载此版本"往往正是为了跟当前文件对照，覆盖掉原来那份很难解释。
   下载是流式写入 `.part` 再 rename，中途失败会清干净临时文件。
4. **历史按"已打开的工作副本所属仓库"展示**（主进程 `requireRepo`）。单窗口客户端里，
   不再让用户选一次"看哪个仓库"，少一个能选错的地方。

**M4 第四轮实现澄清：冲突解决（2026-09-15）**

1. **共同祖先（base）必须单独留存**。update 撞冲突时会做三件事：本地版本改名成
   `<path>.mine`、工作文件换成服务端版本、`entry.base_hash` 更新为服务端版本。
   于是**冲突前的基线哈希被覆盖掉了**——而"本地 / 服务端 / 基线"三方对比正需要它。
   所以 wc.db 迁移 v2 建 `conflicts` 表单独记录 `base_hash`（`entry` 里已经读不到了）。
2. **冲突分两类，界面能做的事完全不同**（`conflicts.reason`）：
   - `both-modified`：双方都改了。三方齐全，文本可合并；二进制只能二选一。
   - `deleted-remotely`：服务端删了、本地改过。**没有服务端内容可对比**，
     选项变成"保留本地（重新纳入，提交时记为 add）"与"接受删除"。
   把这两类混成一个"冲突"会让界面出现"使用服务端版本"却无版本可用的尴尬。
3. **"保留本地"在两类冲突下的语义不同**。`both-modified` 下是把 `.mine` 覆盖回工作文件，
   基线仍是服务端版本 → 状态 `modified`，直接提交即可；`deleted-remotely` 下服务端已无此路径，
   若仍按 `modified` 提交会拿 modify 去撞一个已删除的路径，所以必须**退掉基线条目并重新 add**。
4. **文本/二进制的判定前置**（`core/text.ts`）：美术库绝大多数文件是二进制，必须先判再读。
   规则：采样前 8000 字节，出现 NUL 或不是合法 UTF-8 即判二进制；超过 1 MiB 直接判 `too-large`
   不读内容。返回判别式结果而不是抛异常——"不存在 / 太大 / 二进制"都是**正常业务状态**，
   界面上要分别给不同提示。
5. **解决冲突后的条目 `mtime_ms` 必须置 0**。状态判定的快速路径是"mtime + size 都没变 ⇒
   内容没变"（§6.1），而我们刚把内容装回工作文件、磁盘 mtime 是新的；照实记进条目会让下一次
   `status` 直接报 `normal`——**冲突解决完了却提交不了**。置 0 让快速路径必然不命中。

### 6.6 文件名与平台兼容性

二进制资产库必然跨 macOS / Windows 交换美术资源，文件系统差异是最容易踩坑的地方。**核心原则：服务端永远存规范化的 posix 相对路径（UTF-8 NFC、`/` 分隔），兼容性问题全部在客户端检出/提交边界消化。**

**① Unicode 规范化（NFC/NFD）**

- macOS 生态是重灾区：HFS+ 历史上强制 NFD，APFS 虽不强制但部分工具（git、某些压缩包解压）仍产出 NFD 文件名；Windows/Linux 全部 NFC。
- 规则：
  - **服务端入库唯一形态 = NFC**。`commit/prepare` 的路径合法性校验（§5.3 步骤 5）增加一条：路径非 NFC → `400 PATH_NOT_NORMALIZED`，客户端负责规范化后重试。
  - 客户端扫描工作副本时，对每个路径做 NFC 规范化后再与 `entries` 匹配（macOS 上"看起来同名"的 NFC/NFD 两个文件才不会出现状态错乱）。
  - 提交时若发现同目录下存在 NFC/NFD 互为规范等价的两条路径 → 拒绝提交，报 `NAME_COLLISION`（这类文件在 Windows 上必然互相覆盖）。

**② 大小写不敏感文件系统（Windows NTFS、macOS 默认 APFS）**

- 服务端**保留原始大小写**（不做小写化，保证还原与跨平台一致），但检出时做**大小写折叠冲突检测**：目标工作副本若位于大小写不敏感盘，且服务端子树内存在仅大小写不同的两条路径 → 客户端报冲突清单，检出继续、冲突文件跳过（skip，行为对齐 SVN），状态表标 `case-conflict`。
- **大小写改名**（`a.psd → A.psd`）：在大小写不敏感盘上直接改名是无操作，客户端检测到 case-only 变更时自动走两步提交（内容不变、仅路径变更，服务端按 delete+add 落 `changes` 两行，Tombstone 语义不变）。
- `case-conflict` 检测选项仓库级可关（纯 Linux 团队自建仓库不需要）。

**③ Windows 保留名与非法字符**

- 服务端提交校验拒绝：段名为 `CON/PRN/AUX/NUL/COM1-9/LPT1-9`（不区分大小写）、段以空格或 `.` 结尾、含 `< > : " / \ | ? *` 或控制字符 → `400 INVALID_PATH`（Windows 用户根本无法检出这些文件，入库即埋雷）。
- 客户端 update 时对个别无法在本机落盘的文件（如他人在 Linux 提交的 `aux.txt` 结尾空格变体）走 **skip + 报告**：不阻断整个 update，结果列表明确列出"N 个文件因本机文件系统限制跳过"。

**④ 长路径与特殊文件**

- 路径长度上限：**单段 ≤ 255 字节、全路径 ≤ 1024 UTF-8 字节**（服务端校验；远超 Windows 260 限制，客户端启用 `\\?\` 长路径前缀写盘，启动时检测 `LongPathsEnabled` 未开启则提示一次性授权）。
- **symlink 一律不入库**：扫描发现符号链接 → 警告 + 跳过（v1 不支持；避免目录逃逸与跨平台语义混乱，v2 再评估）。
- 文件 mode 仅记录可执行位（`entries.mode`），Windows 侧忽略。
- **文件占用**（Windows 特有）：Photoshop/Office 持有句柄导致覆盖/删除失败 → 客户端对写盘操作做 3 次退避重试（间隔 1s/2s/4s），仍失败则该文件 skip 并入报告，绝不部分写入（先写临时文件再原子 rename）。

## 7. 传输协议

### 7.1 通用约定

- Base URL：`/api/v1`，JSON 请求/响应 `Content-Type: application/json; charset=utf-8`
- 认证：`Authorization: Bearer <token>`
- 二进制：`application/octet-stream`，`Content-Length` 必填（以支持进度条）
- 时间统一 RFC3339 UTC；路径统一 posix 相对路径、URL 段做 `percent-encoding`、**必须为 NFC**（§6.6）
- 幂等：`PUT /blobs/{hash}`、`DELETE /locks/{path}`、`POST /commit`（commit_id）可安全重试

**错误响应统一结构**（所有非 2xx 响应）：

```json
{ "error": { "code": "OUT_OF_DATE", "message": "工作副本落后于服务端",
             "details": { "head_rev": 42, "paths": ["a.psd"] } } }
```

`code` 是机器可读的稳定标识（客户端按 `code` 分支处理，`message` 仅作展示，可随版本优化文案）。错误码全表：

| HTTP | code | 触发场景 | 客户端处理 |
|---|---|---|---|
| 400 | `INVALID_ARGUMENT` | 参数缺失/类型错误 | 提示开发者错误，不上报重试 |
| 400 | `INVALID_PATH` | 路径含 `..`、保留名、非法字符、超长（§6.6 ③④） | 定位该路径，提示改名 |
| 400 | `PATH_NOT_NORMALIZED` | 路径非 NFC（§6.6 ①） | 客户端静默规范化后重试 |
| 401 | `UNAUTHENTICATED` | token 缺失/过期 | 静默重新登录，失败转登录页 |
| 403 | `PERMISSION_DENIED` | ACL 拒绝 | 按 §4.3 隐藏对应 UI；直接触发不重试 |
| 403 | `ACCOUNT_DISABLED` | 账号被禁用 | 转登录页 + 明确提示 |
| 404 | `NOT_FOUND` | 仓库/路径/修订/锁不存在 | 刷新本地缓存后提示 |
| 409 | `OUT_OF_DATE` | `base_rev ≠ head_rev` | 自动 update 后重走提交流程 |
| 409 | `LOCKED` | 加锁/提交被他人锁阻塞 | 展示锁持有者/备注，提供"请求强制解锁"指引 |
| 409 | `NEEDS_LOCK` | 提交的路径里存在**本人未持锁**的文件（v0.4.17：不再有 glob 过滤，任何变更路径都要求持锁） | 引导一键加锁 |
| 409 | `NAME_COLLISION` | NFC/NFD 或大小写冲突（§6.6 ①②） | 列出冲突路径，人工处理 |
| 409 | `COMMIT_TOKEN_EXPIRED` | prepare 超 5 分钟 | 自动重新 prepare（同 commit_id） |
| 409 | `PURGE_BLOCKED` | purge 目标存在他人锁 | 提示先强制解锁（§3.6） |
| 412 | `HASH_MISMATCH` | 上传 blob sha256 校验失败 | 重算本地哈希，不一致则重新读取文件重传 |
| 413 | `PAYLOAD_TOO_LARGE` | 整块上传超 64 MB | 自动改走分块上传 |
| 422 | `REPO_QUOTA` | 仓库容量配额耗尽 | 停止上传队列，提示联系管理员 |
| 429 | `RATE_LIMITED` | 触发限流 | 按 `Retry-After` 头退避重试 |
| 500 | `INTERNAL` | 服务端内部错误 | 指数退避重试（最多 3 次），仅幂等操作 |
| 503 | `MAINTENANCE` | 维护态（purge/备份中） | 展示维护提示，按 `Retry-After` 轮询 |

**分页约定**（`GET /repos/{repo}/log`、`GET /admin/audit` 等列表接口）：

- 请求：`?limit=&offset=`（`limit` 默认 100、上限 1000）；游标类接口（log 按修订号）可用 `?from=&limit=`。
- 响应信封：`{ "items": [...], "total": 1234 }`；`total` 允许为 `null`（代价高的场景不强求精确值）。
- 大响应（`/manifest`、`/changes` 全量）保持 JSONL 流式，不走该信封。

**重试语义**：

- **可安全重试**（幂等）：所有 GET/HEAD、`PUT /blobs/{hash}`、分块 PUT、`POST /commit`（commit_id 幂等）。
- **不可盲目重试**：`POST /locks`（重试可能成功但产生误导）——以响应为准，超时后先 `GET /locks?path=` 查询再决定；`POST /commit/prepare` 重试安全（同 commit_id 幂等）。
- 网络中断（连接建立后断开）时：`POST /commit` 原样重试同一 commit_id（§5.3）；分块上传按 `GET /blobs/uploads/{id}` 查询已收分块续传。

**M3 实测补充（2026-09-14）**：

- **权限口径收紧**：表头写的"系统管理员**或**本目录 admin"在实现里不成立——除 purge 外，
  所有 `/admin/*` 端点一律要求**系统管理员**（`is_admin`），否则 403 `PERMISSION_DENIED`。
  理由：用户/组/审计/全局统计都是跨仓库的，目录级 admin 没有对应语义。
  目录 admin 只作为 purge 的**第二条件**参与（§3.6 的双条件校验）。
- **新增端点**：`GET /admin/repos/{repo}/acl/preview?user_id=&path=`（有效权限预览器，§8.3）、
  `GET /admin/repos/{repo}/acl/who?path=&level=`（"谁有权限"反查）、
  `GET /admin/repos/{repo}/dirs`（ACL 编辑器的目录下拉）、
  `DELETE /admin/repos/{repo}`（删仓，连带清 ACL/锁/修订）、
  `POST /admin/maintenance/rebuild-refcount` 与 `POST /admin/maintenance/gc`（§3.7）。
- **审计字段是 `detail`（单数）**，与 `audit_log` 表列名一致；`?format=csv` 导出带 UTF-8 BOM
  与中文表头（Excel 直接打开不乱码）。
- **删组可能返回 409 `GROUP_IN_USE`**：组被任何 ACL 规则引用时拒绝删除——否则规则会指向
  不存在的主体，权限静默失效。清理顺序应为"先删仓（连带清该仓规则）→ 再删组 → 再删用户"。

**v0.4.17 契约变更（M4.8）**——这四处字段变化是**破坏性**的，客户端与管理端必须同批更新：

1. `POST /repos` 不再接受 `lock_policy`（传了忽略；取值校验一并删除）；
2. `GET /repos` / `GET /repos/{repo}/info` 的响应删除 `lock_policy` 与 `needs_lock`
   （管理端仓库列表也因此删掉「锁策略」「先锁后提交」两列——后者原本渲染成一个**空白标签**，
   根因是 DB 默认 `''` 而详情页按 `never|auto|always` 枚举写入，同一字段两套语义）；
3. `PUT /admin/repos/{repo}/settings` 只接受 `description`；
4. `POST /repos/{repo}/locks` 不再接受 `kind`，传目录路径直接 400；`user` 对象与用户管理
   接口去掉 `email`。

**「提交说明可空」不是本次的服务端变更**：`POST /repos/{repo}/commit` 的 `message` 一直是
`Option<String>`，空串会原样写进 `revisions.message`。是客户端多加了一道必填校验，本轮去掉。

### 8.3 权限矩阵交互（核心）

左侧是仓库目录树（懒加载，显示已配置规则的目录打标），右侧是"谁 → 什么权限"的规则表：

```
┌─────────────────────────┬────────────────────────────────────────────┐
│  目录树                  │  当前选中：characters/boss                 │
│  ▾ assets               │  ┌──────────────┬──────────┬──────┬───────┐ │
│    ▾ characters     ●   │  │ 主体          │ 权限      │ 屏障  │ 操作  │ │
│      ▾ boss         ●   │  ├──────────────┼──────────┼──────┼───────┤ │
│          secret     ●   │  │ everyone      │ 只读 ▾    │ 否    │ 删除  │ │
│      ▾ mob              │  │ 组 art-lead   │ 读写 ▾    │ 是    │ 删除  │ │
│    ▾ tools          ●   │  │ 用户 zhang    │ 管理 ▾    │ 否    │ 删除  │ │
│    ▸ engine             │  └──────────────┴──────────┴──────┴───────┘ │
│  ● = 该目录有独立规则    │  [+ 添加规则]   从父目录继承：只读          │
└─────────────────────────┴────────────────────────────────────────────┘
```

**辅助能力（M3 实现说明）**

- **有效权限预览器**：选一个用户 + 一个路径，实时展示解析链路（逐层回溯、命中了哪条规则、为何生效），把 §4.2 的算法可视化。这是权限配置最容易出错的地方，必须提供。
  → `GET /admin/repos/{repo}/acl/preview?user_id=&path=`，返回 `{level, reason, steps[]}`。
  `steps` **从最具体的层开始**向父目录回溯（所以"文件自身那一层"通常是 `skip`），
  每层 `outcome ∈ {hit, barrier, miss, skip}`，前端 `el-steps` 直接按这个枚举渲染配色。
- **目录级"谁有权限"反查**：给定目录，列出所有最终有 read/write 的用户（含通过组继承来的），便于交接与审计。
  → `GET /admin/repos/{repo}/acl/who?path=&level=`，每条带 `via` 归因：
  `"直接规则"` / `"通过组 X"` / `"系统管理员穿透"`。归因算法是"用去掉组身份的同一主体再算一次，
  若级别下降则说明权限来自组"。
- **规则冲突/冗余检测**：提示"被更具体的规则完全覆盖，此规则永不生效"。
  → M3 只做了弱提示：规则列表每条带 `shadowed: bool`（该规则是否被同级更具体的规则完全覆盖）。
  完整的可视化冲突提示留到 M5。
- **批量套用**：把一组规则套用到多个目录（新建子目录时的常见需求）。→ **未实现**，留 M5。

## 9. 安全设计

### 9.1 认证与账号供给（LDAP + 本地）

**统一登录入口**：`POST /auth/login` 只有一个。服务端按以下顺序分发：

1. 本地存在 `source='local'` 的同名用户 → 本地 argon2id 校验；
2. 否则若 LDAP 已启用 → 走 LDAP 流程；
3. 两者皆不适用 → 统一返回"用户名或密码错误"（不泄露账号存在性）。

**LDAP 登录流程**（服务账号 bind + 用户 bind 两段式）：

```
1. 用户提交 username / password
2. 服务账号 bind → 在 user_base 下按 user_filter 搜索 (uid={username})
3. 取得用户 DN → 用"该 DN + 用户输入的密码"再次 bind，验证通过即认证成功
4. 读取属性映射：display_name ← cn，external_id ← entryUUID（**v0.4.17：不再读取 `mail`**）
5. 本地 upsert：
   · 不存在 → 创建用户（source=ldap，密码不落库）
   · 已存在 → 刷新 display_name / ldap_dn（登录即同步）
6. 本地 disabled=1 的用户即使 LDAP 验证通过也拒绝登录（本地封禁优先）
7. 与本地用户无差别签发会话 token
```

**首个登录用户 = 系统管理员**：

- 条件：`users` 表为空 **且** `auth.first_user_admin = true`（默认 true）。
- 满足时，第一个成功登录的用户（本地或 LDAP 均可）在**同一事务**内被授予 `is_admin=1`，审计记 `user.first_admin`。事务内判定天然规避并发竞争（SQLite 串行写）。
- 可通过配置关闭；关闭后改用 `--create-admin <用户名>` 显式初始化。
- 管理页用户列表对首位管理员做标注，避免误降权导致系统失去管理员（降权前二次确认 + 审计）。
- **实现澄清（M3 修复）**：判定条件是"登录时 `users` 表里只剩这一个用户"（`COUNT(*) == 1`），
  实现在**同一写事务**内完成，天然规避并发竞争。原实现**只在 LDAP 分支**调用
  `grant_first_admin_if_needed`，本地用户登录拿不到管理员，与"本地或 LDAP 均可"的方案声明
  直接冲突——因为所有冒烟脚本都预建管理员，这个偏差一直没暴露，直到 M3 补认证集成测试才发现。
  修复后 `POST /auth/login` 对两条来源都会走同一段首登判定。
- **对既有部署的影响**：升级后若库中恰好只有一名用户，该用户下次登录会被授予 `is_admin=1`。
  若不希望如此，先在配置里关闭 `auth.first_user_admin`。

**安全约束**：

| 项 | 规则 |
|---|---|
| 密码 | LDAP 密码**绝不落库**，LDAP 用户 `password_hash` 为 NULL，不能改用本地密码登录 |
| 用户名冲突 | LDAP 建号时若同名本地用户已存在 → 拒绝该 LDAP 登录并审计（`username_conflict = reject`），需管理员处理，不自动合并 |
| 身份稳定性 | 以 `external_id`（entryUUID / objectGUID）为稳定标识，DN 或显示名变更不影响账号归属 |
| 传输 | 生产强制 `ldaps://` 或 starttls；明文 `ldap://` 需显式 `allow_insecure=true`（仅内网调试），启动时告警 |
| 降级保护 | LDAP 服务不可用返回明确错误 `LDAP_UNAVAILABLE`，**不静默回退本地认证**——避免"LDAP 一挂，人人走本地后门" |
| 限流 | 登录失败退避对两种来源同样生效；LDAP bind 失败同样计数 |

**API 增量**：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/auth/providers` | `{ldap: {enabled}, local_enabled, first_user_admin}`；登录页据此渲染（如"域账号登录"提示） |
| POST | `/auth/login` | 入口不变；登录响应的 `user` 中带 `source`（local/ldap） |

### 9.2 安全基线

| 面 | 措施 |
|---|---|
| 口令 | argon2id（`m=64MiB, t=3, p=4`），不存明文、不可逆 |
| 口令强度（v0.4.17） | **≥8 个字符**（按**字符**计数，不是字节）**且**必须同时含数字 / 大写字母 / 小写字母 / 符号四类；上限 256 字符。唯一实现入口 `auth/password.rs::validate_policy()`，建用户 / 重置密码 / 改密 / CLI 建管理员四条路径共用；**登录路径不校验强度**（LDAP 用户的口令策略在目录服务侧，套用本策略会把老账号锁在门外）。管理端表单做同规则的即时校验，但**以服务端为准** |
| 会话 | 32 字节 CSPRNG token，DB 只存 token 的 sha256；TTL 默认 30 天；可吊销；登录失败退避限流 |
| 传输 | 内建 rustls 支持（`--tls-cert/--tls-key`），或置于 Nginx/Caddy 之后；强制 HTTPS 时校验 `X-Forwarded-Proto` |
| 授权 | 每次请求服务端重新解析；**不存在客户端可信路径**；逐路径校验提交 |
| 路径穿越 | 统一 `normalize_path()`：拒绝 `..`、绝对路径、`\`、控制字符、超长段、`.` 开头保留段；入库前归一 |
| 上传防护 | 大小上限（可配）、sha256 强校验、临时文件隔离、磁盘配额（按仓库限制） |
| 审计 | 登录/权限变更/强制解锁/提交/管理操作全量落库 + JSONL 归档 |
| 传输完整性 | 下载 `ETag`=blob hash + 客户端校验；上传服务端复算 |
| 依赖安全 | `cargo deny` / `cargo audit` + `npm audit` 纳入 CI |

## 10. 性能与容量

### 10.1 预期瓶颈与对策

| 环节 | 风险 | 对策 |
|---|---|---|
| 提交 | SQLite 单写者 | WAL + 短事务；提交仅写变更行；预计单仓库 50~200 提交/秒足够 |
| 列目录 | 历史修订的范围扫描 | HEAD 走 `head_entries`（O(log n)）；历史修订低频且有索引 |
| 上传 | 大文件带宽瓶颈 | 客户端并发 4~8、先问后传、`Range` 续传、服务端 `sendfile` |
| 哈希 | 大文件 CPU | 流式 sha256 + `sha2` 的 SHA-NI 加速；worker_threads 并行；mtime+size 启发式跳过 |
| 磁盘 | 无限增长 | CAS 去重 + refcount GC（refcount 可重建）+ 仓库配额 + 用量看板 |
| GC 自愈 | refcount 漂移 | 启动脏检测 + `rebuild_refcount()` 全表重建；`changes` 始终是引用事实来源 |
| 内存 | 清单类响应过大 | 所有列表接口分页/JSONL 流式，不一次性构造大数组 |

### 10.2 容量设计目标（v1）

- 单仓库：100 万文件 / 10 万修订
- 单文件：默认上限 8 GB（可配）
- 并发客户端：500 在线 / 50 并发传输
- 元数据：1000 万条 `changes` ≈ 1.5 GB SQLite，完全可控

### 10.3 可扩展性预留

- DB 访问收敛在 `storage/` 模块（用 SQL 方言子集），未来切 PostgreSQL 只改这一层
- Blob 访问抽象为 `trait BlobStore`，未来可加 S3/OSS 后端（冷数据下沉）
- 服务端无状态部分（HTTP 层）可水平扩展；有状态部分目前是单机 SQLite + 本地磁盘，需要时演进为 PG + 对象存储

### 11.1 运行方式

```bash

### 11.2 配置示例

```toml
[server]
listen = "0.0.0.0:8443"
data_dir = "/var/lib/b-artifact"
base_url = "https://svn.example.com"
tls_cert = "/etc/b-artifact/tls.crt"
tls_key  = "/etc/b-artifact/tls.key"

[auth]
session_ttl_days = 30
max_login_failures = 5
backoff_seconds = 60
first_user_admin = true          # 首个登录用户自动成为系统管理员

[ldap]                           # 企业域账号统一登录
enabled = false
url = "ldaps://ad.example.com:636"
allow_insecure = false           # 明文 ldap:// 仅限内网调试
bind_dn = "cn=svc-b-artifact,ou=service,dc=example,dc=com"
bind_password = "******"
user_base = "ou=people,dc=example,dc=com"
user_filter = "(uid={username})" # AD 常用: (sAMAccountName={username})
attr_display_name = "cn"
attr_uid = "entryUUID"           # AD 用 objectGUID
username_conflict = "reject"     # 与本地同名用户冲突时拒绝 LDAP 登录
# v0.4.17：attr_email 已删除（不再读取 mail）

[storage]
compression = "auto"          # off | auto | always
max_file_size_mb = 8192
chunk_threshold_mb = 64

[lock]
default_ttl_hours = 168        # v0.4.17：default_policy 已删除（只剩"先锁后提交"一种语义）

[gc]
enabled = true
schedule = "0 3 * * *"        # 每天 03:00
grace_hours = 24
```

## 12. 测试方案（单元测试 + 功能测试）

### 12.1 总体策略

测试按金字塔分层，越往下越多、越快、越隔离；每个里程碑的"测试全绿"是硬性交付条件（与 §14 交付物表对应）。

| 层 | 对象 | 工具 | 运行时机 |
|---|---|---|---|
| 单元测试 | server 各模块 / admin 组件与 stores / client 的 wc-core | cargo test / Vitest / Vitest | 每次提交（秒级） |
| 功能测试 | 服务端 HTTP API（起真实进程） | cargo 集成测试 + reqwest | 每次提交（分钟级） |
| E2E | 管理端页面 / Electron 客户端 ↔ 真实服务端 | Playwright | 每里程碑全量 + 发版前 |
| 压测 | 造数大仓库 | scripts/ 造数脚本 | M1.5（见 §14） |

三端职责分离：**server** 的测试重心在核心语义（Path-History / ACL / 锁 / 提交 / GC）的单元覆盖 + API 功能测试；**admin** 重心在权限矩阵交互；**client** 重心在 wc-core 纯 Node 引擎（不依赖 Electron，可直接跑单测）。

### 12.2 服务端单元测试（cargo test）

按 §3.5 模块划分逐模块覆盖，**每条 v0.4 定死的语义都必须有对应用例**：

| 模块 | 必测语义 |
|---|---|
| path_history | ①目录 Tombstone 覆盖判定（自身最近 change + 祖先链最近 delete-dir）②restore-as-commit（恢复是新提交、可再恢复）③HEAD 快路径与历史回溯结果一致 ④目录存在性由"存活子文件 + 未被 Tombstone 覆盖"推导 ⑤任意修订取单文件 = 路径历史倒序第一条 |
| blob（CAS） | sha256 去重（同内容只落一份）、zstd auto 阈值（收益 ≤5% 不压）、原子写（写入中断不产生半文件）、并发写同一 blob 只落盘一次 |
| acl | 继承屏障与"用户是否命中"解耦、自深向浅命中即返回、同层 user > group > everyone、同级拒绝优先、默认拒绝 |
| lock | 同路径被他人持有效锁 = 冲突并返回持有者详情、**本人重复加锁幂等**、目录路径被拒（400）、强制解锁写审计（reason 必填）、**提交时每个变更路径都必须本人持锁**（未持锁返回 412 + 路径清单）、TTL 过期即失效（过期锁不再阻塞加锁/提交）、续期返回绝对到期时间、`owner=me` 跨副本锁列表 |
| commit | commit_id 幂等短路（重放返回同一结果）、commit_token 五元组绑定与失效（换用户/换 base_rev/篡改 changes 均拒绝）、base_rev 严格相等、pending_commits 过期、路径合法性校验（§6.6：NFC / 保留名 / 长度上限） |
| gc | refcount 增减、宽限期、物理删除前排除未过期 pending_commits、`rebuild_refcount()` 全表自愈后与 changes 事实一致 |
| auth | argon2 校验、LDAP mock 两段式 bind、首登管理员同事务授予、username_conflict=reject、LDAP 不可用不回退本地认证、**口令强度策略（8 字符下限按字符计数 / 四类字符齐备 / 256 上限 / `P@ssw0rd`·`12345678`·`Abcdefg1` 等必须被拒）** |

**测试环境约定**：每个用例独立 tempdir + 独立 SQLite 文件（不用共享库）；随机数据用固定种子（xorshift64）保证可复现；涉及并发的用 `#[tokio::test]`。

**覆盖率目标**：核心模块（path_history / acl / lock / commit / gc）行覆盖 ≥ 80%，用 cargo-llvm-cov 度量，作为 M2 完成的验收项之一。

### 12.3 服务端功能测试（HTTP API 级）

**形态**：`server/tests/integration_*.rs`——启动真实 axum 服务（随机端口 + 临时 data 目录），用 reqwest 按 §7.2 接口清单逐场景走 HTTP。

**断言三层**：HTTP 状态码与错误码（§7.1 约定）→ 响应 JSON 结构 → 副作用（SQLite 行数/内容 + 磁盘 blob 文件存在性）。

**核心场景矩阵**：

| 域 | 场景 |
|---|---|
| 认证 | 登录/登出/token 过期与失效、首登自动管理员、LDAP 不可达返回 502 且不回退、disabled 用户被拒 |
| 仓库 | 建仓（**只带名称与描述**）、查询、存储用量统计 |
| checkout / update | 全量检出、目录级部分检出、子树增量更新、目录被删除后的 update 行为 |
| 提交 | 两阶段流程、prepare 返回缺失 blob 清单、base_rev 过期返回 409、commit_id 重放幂等、commit_token 挪用被拒 |
| 分块上传 | init / put（乱序）/ complete、断点续传（中断后重传）、分块 hash 不符整体拒绝 |
| 锁 | 文件锁、**目录路径加锁被拒**、加锁冲突返回持有者详情、强制解锁（reason 必填）、**无锁提交一律被拒（412 NEEDS_LOCK + 路径清单）**、部分文件持锁仍被拒、TTL 过期后本人需重新加锁、refresh 续期、过期锁惰性清理 |
| 路径兼容（§6.6） | 非 NFC 路径提交返回 400 PATH_NOT_NORMALIZED、Windows 保留名 / 非法字符返回 400 INVALID_PATH、同目录 NFC/NFD 规范等价路径返回 409 NAME_COLLISION、case-only 改名落 delete+add 两行 |
| 删除与 purge | L1 删除可恢复、L2 purge 二次确认、目标下存在**他人锁 → 拒绝**、本人锁自动释放并审计、purge 后 blob 进 GC 队列、宽限期后磁盘回收 |
| 错误码 | 401 / 403 / 404 / 409 / 412 / 413 / 422 / 429 / 503 的 code 与语义逐条对照 §7.1 错误码表；分页参数边界（limit=0、limit>1000 截断） |

每个功能场景附一条 **CLI 冒烟命令**回归（CLI 是 API 的第一个消费者，API 变更会被立即暴露）。

>   省掉下一轮靠猜的时间。截图留档。
> - **这一轮抓到的 4 个真 bug**：① `wc:commit`/`wc:update` 后 `adopt` 同一实例时先 `close`
>   再赋值 → 把自己关掉（后续 `database is not open` / `statement has been finalized`）；
>   ② 响应式数组过 IPC 被拒（"An object could not be cloned."），载荷需 JSON 归一化；
>   ③ 状态表用 `isCommittable` 当"可勾选"判定 → `unversioned` 被置灰、**"标记新增"永远点不动**；
>   ④ 漏 import Element Plus 的 CSS → 界面无样式（组件单测因替身而看不见，靠截图才发现）。

> **M4 第四轮实测（2026-09-15）：冲突解决落地**。客户端单测从 302 涨到 **364**

> **45 项**，新增的三步覆盖了完整链路：

> 1. **制造冲突**：本地改两个文件，同时让"别人"在服务端改一个、删一个 → 点"更新" →
>    断言提示冲突、冲突页列出两条、顶栏与菜单角标显示 2。

> **M4.8 需求变更轮的新增测试面（v0.4.17）**。本轮改动集中在客户端交互与服务端锁语义，
> 单测要覆盖的"纯函数"也随之变化：
>
> - **目录树构建**（`utils/tree.ts`）：`StatusItem[]` → 树，含目录汇总"变更 N"、默认展开策略、
>   只看变更的过滤、以及"目录条目自身不可提交"。
> - **自动补锁编排**：给一批路径 → 分出"已持锁 / 需加锁 / 被他人持锁"，加锁失败即中止。
>   这条逻辑必须抽成纯函数（输入是 `StatusItem[] + LockInfo[]`，输出是待执行计划），
>   否则"部分加锁成功后提交失败"这种半成品状态没法测。
> - **口令策略**：服务端 `validate_policy` 的边界用例（7/8/9 字符、纯数字、纯小写、
>   带空格、中文按字符计数、257 字符上限），管理端表单校验与它**规则一致**（同一张用例表跑两边）。
> - **自动同步**：watcher 的防抖与抑制逻辑（自写入不触发、`.b-artifact/` 与忽略规则命中的路径不触发）
>   抽成可注入时钟的纯函数，不依赖真实 `fs.watch`。
> - **E2E 必须补的三条**：目录树里新建文件 → 默认不勾选 → 勾选 → 提交（自动补锁可见）；
>   树上删除目录（多文件各自持锁）；`fs.watch` 生效下**在系统文件夹里改文件**→ 界面状态自动变化
>   （这一条是本轮的原始诉求，必须在真实 Electron 进程里验，不能只靠单测）。
>
> **M4.8 实测（2026-09-15）**：客户端单测（新增 `utils/tree` 16 / `main/watch` 9 /

### 12.6 端到端与回归门禁

- `tests/e2e/`：起真实服务端 → 用 CLI（或客户端 headless 模式）完成完整生命周期：建仓 → 检出 → 修改 → 加锁 → 提交 → 删除 → 恢复 → purge → 触发 GC → 校验磁盘回收。

## 15. 风险与开放决策点

### 15.1 已识别风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 无分支模型 | 低 | **已确认为设计决策**（2026-09-14）：无分支与 merge 需求，单主干线性历史即满足场景 |
| SQLite 单机单写 | 中 | 单机足够支撑目标规模；预留 PG 迁移层 |
| 二进制无法合并，冲突靠人 | 中 | 严格锁策略 + 冲突绝不丢数据 + 客户端对比 UI |
| Electron 包体积 ~150 MB | 低 | 内网分发可接受；备选 Tauri（同为 Rust 栈，体积 ~10 MB）—— 若在意可切 |
| 全量 CAS 磁盘增长快 | 中 | 去重 + 压缩 + GC（refcount 可重建）+ 配额 + 用量看板 |
| 历史修订列目录较慢 | **已实测升级为 P0**（原判"低"） | **M1.5 实测推翻**：`list_dir_at_root_head` 在 240k 文件档位 **22.3 秒**、`full`（1M 文件 / 100k 修订）档 **86.9 秒**；`tree?rev=` 端到端 19.9 秒 / **75.5 秒**。HEAD 快路径同样不成立（`list_dir_head(root)` 为返回 **1 个条目**要读整张表：240k 档 206 ms、`full` 档实测 **762 ms**；`tree?depth=1` 端到端 `full` 档 **732 ms**）。**修复见压测报告 §6（B4 `parent_path`）+ §4（B1 前缀下推），两者互补缺一不可**。**M1.6 已修（2026-09-14）**：`list_dir_head_root` 206 ms → **5 µs**、`dir_exists_at_head` 166 ms → **14 µs**、`tree_root_depth1` 端到端 203.87 ms → **210 µs**；**非 HEAD 修订列目录仅 3×（`m` 档 7.4 s），是本轮唯一未达标的核心项**，见 `docs/压测报告-M1.6.md` §6 |
| 并发度受全局单连接限制 | **高**（原未识别） | **M1.5 新发现（B6）**：`AppState.db: Mutex<Connection>` 使并发度结构性恒为 1——并发 8→32（4×）时 DB 端点吞吐 +0.2%~+8%（`repo_info` 甚至 −7%），p50 涨 ~4 倍；同期 `download_blob` 因不长期持锁拿到 +118%。**M1.6 已落地（B6）**：自研阻塞式 `DbPool`（WAL 多读单写，写事务 `BEGIN IMMEDIATE`），`tree_root_depth1_c8` 5/s → **3451/s**。**调参结论：默认池大小 8 → 4**（完整跑口径 `download_blob_c8` 3529/s vs pool=8 的 459/s）；`block_in_place` 实测更慢，**默认关闭**，留 `B_ARTIFACT_DB_BLOCK_IN_PLACE=1` 开关 |
| 提交延迟随仓规模超线性膨胀 | **高**（原未识别） | **M1.5 新发现（B5）**：`changes.blob_hash` 无索引，`apply_commit_tx` 每条变更反查整仓历史；`changes` 行数 667× → `apply_commit_1000` 延迟 **941×**（`m` 档 **67.5 秒**、`full` 档 **267.8 秒**/次）。**加部分索引 + 把 `byte_delta` 移出提交关键路径**（压测报告 §7）。**M1.6 已修（B5）**：`apply_commit_1000` 67.5 s → **21 ms**（~3213×），已与仓规模解耦；`byte_delta` 因本轮实测不再构成瓶颈、暂未移出关键路径，留待 M2 观察 |
| Tombstone 误删子树 | 中 | purge 二次确认（`confirm_name`）+ 维护态写互斥 + 审计；普通 rm 与 purge 分离权限 |
| 网络抖动导致重复提交 | 中 | `commit_id` 幂等表 + 服务端短路返旧 rev（§5.3） |

## 附：与 SVN 的对照

| SVN 概念 | 本项目 | 差异 |
|---|---|---|
| `trunk/branches/tags` | 单主干 + 修订号 | v1 不做分支 |
| `.svn/pristine` | `.b-artifact/pristine` + 全局硬链接缓存 | 增加跨副本共享，省磁盘 |
| `svn:needs-lock` 属性 | 无 —— **一律要求先锁**（v0.4.17 去掉了 glob 白名单） | 比 SVN 更严格：不存在"某些文件可以不锁"的配置 |
| `svn lock` | 同 | 增加锁 TTL、审计、管理页强制解锁 |
| `authz` 文件（路径规则） | `acl_rules` 表 + 管理页 | 可视化配置 + 有效权限预览 |
| `svn checkout --depth` | 目录树勾选式部分检出 | 更符合"只要某个子目录"的实际诉求 |
| 全局修订号 | 每仓库独立修订号 | 隔离仓库间干扰，便于独立归档 |
