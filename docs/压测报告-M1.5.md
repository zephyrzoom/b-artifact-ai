# b-artifact M1.5 性能压测报告

> 对应方案 §14 里程碑 **M1.5 性能压测**，交付物 = **压测报告 + 瓶颈清单**（§12.8）。
>
> 结论先行：**Path-History 的两条核心查询（HEAD 快路径列目录 + 历史推导列目录）在
> 1M 文件档位下不可用**，`checkout` / `tree` 这条链路因此整体不成立。根因不是算法选型，
> 而是四项**可在小时级修掉的工程缺陷**，外加一项需要在 M2 一并处理的并发结构问题。
> 共定位 **6 个瓶颈**，其中 **B1（前缀 `LIKE` 未下推索引）、B2（语句重复 prepare）是
> M2 开工前的阻断项**，B4/B5/B6 建议同批修（改动都在 schema/DDL 层面，合并做一次迁移
> 比拆开做两次便宜）。

| 编号 | 瓶颈 | 性质 | 优先级 |
|---|---|---|---|
| B1 | 前缀 `path LIKE ?` 无法下推索引，退化为整仓扫描 | 查询计划 / DDL | **P0 阻断 M2** |
| B2 | 热路径语句未走 prepared-statement 缓存，逐次重新 prepare | 代码 | **P0 阻断 M2** |
| B3 | refcount GC 用相关子查询，`O(blob × 全仓历史)` | SQL 写法 | P2 |
| B4 | `head_entries` 无 `parent_path` 列，列目录须读**全部后代**再折叠 | schema | P1 |
| B5 | `changes.blob_hash` 无索引，每次提交反查整仓历史 | DDL | P1 |
| B6 | 全局单 `Mutex<Connection>`，并发度结构性恒为 1 | 架构 | P1（M2 处理） |

**六项瓶颈在 `full` 档（1M 文件 / 100k 修订，即 §14 目标规模）的实测代价**：

| 操作 | `full` 档实测 | 说明 |
|---|---|---|
| `list_dir_at_root_head`（列仓库根目录 @head） | **86.9 s** | 只要 1 层结果，代价却是分钟级 |
| `GET /tree?prefix=&depth=1&rev=<head/2>`（端到端 HTTP） | **75.5 s** | 同一条链路走完 HTTP 层的形态 |
| `list_dir_head_root`（HEAD 快路径，返回 **1** 个条目） | **762 ms** | 快路径也没快起来 |
| `apply_commit_1000`（1000 条变更的提交） | **267.8 s** | 写路径同样不成立 |
| `GET /tree?depth=1`（HEAD 端到端） | **732 ms** | `depth` 不参与 SQL，最便宜的调用也是秒级 |
| 并发 8 → 32 的吞吐增益（DB 端点） | **±0.0% ~ +7%** | 加并发只增延迟，不加吞吐 |

- 报告版本：v1
- 测量日期：2026-09-14
- 被测版本：M1 完成态（单测 22 + 集成 5 + 冒烟 34 全绿）
- 工具链：`rustc 1.95.0` / `cargo 1.95.0` / SQLite（rusqlite bundled）
- 原始数据：`bench-results/`（逐基准 JSON + 查询计划证据文本）

## 1. 测量目标与范围

§14 对 M1.5 的要求是：**造数脚本：单仓库 1M 文件 / 100k 修订；测 list、checkout、update、
commit 延迟；refcount GC 全量重建耗时**。

三条链路在 M1 阶段的可测性不同，这里如实划清边界：

| 方案要求 | M1.5 的测法 | 说明 |
|---|---|---|
| list 延迟 | ✅ 直接可测 | `tree?prefix=&depth=`（HEAD 快路径与历史推导路径各测一组） |
| checkout 延迟 | ◐ 服务端分解项可测 | 完整 checkout 由 M4 客户端驱动。服务端可测部分是「目录遍历」+「blob 下载」，本报告分别给出并给出推算式 |
| update 延迟 | ◐ 服务端分解项可测 | 同上；`blobs/missing`（差异探测）+「缺块下载」已测 |
| commit 延迟 | ✅ 直接可测 | 存储层 `apply_commit_tx`（事务内回滚，可重复测）+ HTTP 两阶段提交真实落库 |
| refcount GC 全量重建 | ✅ 直接可测 | 两种写法对照（见 §5） |

> 完整 checkout / update 的端到端延迟**本报告不声称已测**，待 M4 客户端就绪后补测。
> 本报告给出服务端各分解项的实测值与推算公式，足以判断服务端是否成为瓶颈。

## 2. 方法与工具

### 2.1 造数脚本 `scripts/gen_fixture.py`

直接产出**自洽的可用仓库**（不是"一堆随机文件"）：既写 SQLite 元数据库，也落真实
blob 文件，服务端启动即可对外服务。数据模型与 §3.3 Path-History 完全一致
（`revisions` / `changes` 增量 / `head_entries` / `blobs`），schema 直接复用
`server/migrations/*.sql` 作为唯一真源，因此**造数结果与服务端写入路径同构**。

档位（`N = top × mid × leaf × files_per_dir`）：

| 档位 | 布局 (top×mid×leaf×files) | 存活文件 | 修订 | `changes` 行 | `head_entries` 行 | blob 池 | DB 体积 | 造数耗时 |
|---|---|---|---|---|---|---|---|---|
| `xs` | 5×5×5×8 | 1,000 | 200 | 2,990 | 1,000 | 800 | 1.1 MB | 43 s |
| `s` | 20×20×10×10 | 40,000 | 1,000 | 49,800 | 40,000 | 2,000 | 17.6 MB | 204 s |
| `m` | 40×40×15×10 | 240,000 | 20,000 | 438,800 | 240,000 | 3,000 | 136 MB | 284 s |
| `full` | 100×100×10×10 | **1,000,000** | **100,000** | **1,995,000** | **1,000,000** | 4,000 | **609 MB** | 368 s |

> 每档数字取自同目录 `fixture-<scale>.json`，**不是估算值**。`full` 档即 §14 要求的
> "单仓库 1M 文件 / 100k 修订"目标规模，**已真实造出并完成测量**。

路径布局三段式 `assets/{p:04d}/{m:04d}/{l:03d}/f{k:02d}.bin`，便于把
"浅层大目录"与"深层小目录"两种查询形态分开测。

**跨档位可比性设计**：压测时把前缀固定在子树规模恒定的位置（每个末级目录固定 10 个
文件），这样跨档位比较时**唯一变化的量是全仓历史长度**，把"扫描量随历史增长"这一项
单独隔离出来——这是本报告能定位到根因的关键。

### 2.2 压测 harness `server/benches/m15_bench.rs`

`harness = false` 的 bench 目标，本质是一个独立可执行程序，因而能复用
`dev-dependencies`（reqwest 等）而不污染服务端二进制。

它**在进程内起真实 axum**（随机端口）+ reqwest 客户端，装配与线上完全一致的
`AppState`，分四组测量：

| 组 | 内容 | 为什么需要 |
|---|---|---|
| `env` | 文件 open+read、SQLite 点查、**语句 prepare 成本** | 建立环境底噪，把"环境开销"从被测代码耗时里剥出来 |
| `sweep` | 生产 SQL vs 等价重写的**查询计划对照** | 证明瓶颈来自查询计划，而不是别处 |
| `storage` | 直连库调 `repo::*` | 排除 HTTP/序列化干扰，测纯存储层 |
| `http` / `conc` | 端到端串行 / 多并发档位 | 测真实延迟与扩展性 |

两条工程约束值得记下来：

1. **采样预算**（`--budget`，默认 15s/基准）：本报告的一个核心发现就是"某些路径在大档位
   下慢到不可用"，如果 harness 傻跑固定次数，一轮压测会变成几小时。预算用尽即停止采样，
   并在报告里标注实际样本数——**"跑不完"本身就是结论**。
2. **重基准的采样数自适应**：代价为 `O(存活文件 × 路径深度)` 的那批基准
   （`list_dir_at_root_head`、`list_dir_at_l1_mid`、`tree_root_hist_rev`）是**判断
   "checkout 是否可用"的核心证据，必须跑**；但单次调用在 `full` 档就要一分钟量级。
   因此存活文件 > 20 万时把采样数从 3 降到 1（`--heavy on(n=1)`，报告里如实标注
   `n=1` 时 p50=p95=p99 无区分度）。`--heavy off` 是留给 CI 的逃生开关。

   同理，写入路径的 `apply_commit_{10,100,1000}` 在 `changes > 100 万` 时降到单次采样、
   不预热——原因见 §5（B5），单次提交的代价是 `O(本次变更数 × 全仓历史行数)`。

   这两处"降采样"不是为了让数字好看，而是为了让**增长趋势**能在有限墙钟时间里被观察到：
   `xs/s/m/full` 四个点连起来的斜率就是瓶颈证据，`full` 档的作用是确认量级而非取精确分位。

### 2.3 测量口径

- 延迟一律取 **p50 / p95 / p99**；`n` = 实际样本数。
- 所有延迟数字来自 **release（bench profile，`lto=thin`）**。debug 数字无参考价值
  （同一个 `login_argon2id`，debug 2.44s vs release 116ms，差 21 倍）。
- 并发组固定请求数、逐并发档位报告吞吐与尾延迟。

## 4. 根因分析（一）：前缀 `LIKE` 无法下推索引（B1，P0）

### 4.1 现象

`xs` 档位（1000 文件 / 2990 行 changes）上，**列同一个仓库根目录**的两种写法差了 **107 倍**：

| 基准 | 路径 | 返回条目 | p50 |
|---|---|---|---|
| `list_dir_head_root`（HEAD 快路径，走 `head_entries`） | `""` | 1（`assets`） | 726 µs |
| `list_dir_at_root_head`（历史推导路径，走 `changes` 窗口函数） | `""` | 1（`assets`） | **78.06 ms** |

而且 `list_dir_at_*` 的耗时**与返回条目数无关**：返回 1 个条目的根目录（78.06ms）比
返回 5 个条目的 `assets/0000`（15.66ms）还慢——说明代价不在"结果规模"，而在"扫描规模"。

### 4.2 证据：`EXPLAIN QUERY PLAN`

生产代码（`repo.rs` 的 `last_changes_under` / `list_dir_head`）用的是：

```sql
WHERE repo_id = ?1 AND rev <= ?2 AND path LIKE ?3 ESCAPE '\'
```

拿**真实的 `full` 档库**（`changes` 1,995,000 行 / `head_entries` 1,000,000 行）跑
`EXPLAIN QUERY PLAN`，生产写法退化成整仓扫描（完整输出见
`bench-results/plan-evidence-full.txt`）：

```sql
-- changes 侧：生产写法（prefix LIKE）
  CO-ROUTINE last
  CO-ROUTINE (subquery-3)
  SEARCH changes USING INDEX idx_changes_rev (repo_id=? AND rev<?)
  USE TEMP B-TREE FOR ORDER BY
  SCAN (subquery-3)
  SCAN last

-- head_entries 侧：生产写法（prefix LIKE）
  SEARCH head_entries USING INDEX sqlite_autoindex_head_entries_1 (repo_id=?)

-- changes 侧：等价重写（prefix GLOB）
  SEARCH changes USING INDEX idx_changes_path (repo_id=? AND path>? AND path<?)
  SCAN (subquery-3) / SCAN last        ← 无 USE TEMP B-TREE

-- head_entries 侧：等价重写（prefix GLOB）
  SEARCH head_entries USING INDEX sqlite_autoindex_head_entries_1 (repo_id=? AND path>? AND path<?)
```

**这里有一个容易看错的陷阱，值得单独说明**：生产写法出现的也是 `SEARCH ... USING INDEX`，
不是 `SCAN table`。如果只看"有没有用索引"，会得出"已经走索引了"的错误结论。真正要看的
是**关键列有没有被界住**：

| | 生产（LIKE） | 重写（GLOB） |
|---|---|---|
| 用没用索引 | ✅ 用了 | ✅ 用了 |
| `path` 列有界？ | ❌ **无界**（只界了 `repo_id`） | ✅ `path>? AND path<?` |
| 等价于 | 该仓库**全部**历史行 / 全部条目 | 该前缀下的行 |
| 额外开销 | 窗口函数还要 `USE TEMP B-TREE FOR ORDER BY` | 索引序即 `path` 序，排序消失 |

`SEARCH changes USING INDEX idx_changes_rev (repo_id=?)` 应读作：**顺着 `idx_changes_rev`
把该仓库的每一行都读一遍**。索引在这里只起到"按 repo_id 分组扫描"的作用，没有任何过滤
能力——所以它在 1M 文件档位下等价于全表扫描。

原因：SQLite 只有在 **`case_sensitive_like=ON`**（或改用 `GLOB` / 范围条件）时才肯把
前缀 `LIKE` 下推成索引范围扫描。而 `db::open()` 没有设置这个 pragma，默认 `OFF`，
于是：

- `changes` 侧：查询计划从 `O(该前缀下的历史行数)` 退化为 **`O(整个仓库的历史行数)`**；
- `head_entries` 侧：HEAD 快路径同样中招——`list_dir_head_leaf`（只要 8~10 个条目）
  却要扫完整张 `head_entries`。**所谓"快路径"其实并不快。**

### 4.3 影响量化（跨档位放大）

`sweep` 组的做法：同一份数据、同一个前缀、同样的返回结果，只把 SQL 从 `path LIKE 'pfx%'`
换成等价的 `path GLOB 'pfx*'`。**加速比随仓规模单调放大**，这就是"扫描量随历史增长"的
直接证据：

`head_entries` 前缀查询（末级目录 `assets/0000/0000/000/`，固定返回 10 个条目）：

| 写法 | p50 @ `xs` | p50 @ `s` | p50 @ `m` | p50 @ `full` | `full`/`xs` 放大 |
|---|---|---|---|---|---|
| `head_prefix_like_leaf`（生产） | 92.8 µs | 3,851 µs | 24.0 ms | **88.4 ms** | **952×** |
| `head_prefix_glob_leaf`（重写） | 13.7 µs | 15.4 µs | 21 µs | 15 µs | 1.1× |
| **加速比** | 6.8× | **250.6×** | 1,145.0× | **6,029.1×** | — |

`changes` 前缀窗口查询（同一前缀）：

| 写法 | p50 @ `xs` | p50 @ `s` | p50 @ `m` | p50 @ `full` | `full`/`xs` 放大 |
|---|---|---|---|---|---|
| `changes_prefix_like_leaf`（生产） | 449 µs | 9,337 µs | 75.2 ms | **299.3 ms** | **667×** |
| `changes_prefix_glob_leaf`（重写） | 117 µs | 101 µs | 112 µs | 105 µs | 0.9× |
| **加速比** | 3.9× | **92.8×** | 674.0× | **2,846.3×** | — |

**最有力的一条证据**：`list_dir_head_leaf` 与 `list_dir_head_leaf_cslike` 是**同一个
`repo::list_dir_head` 函数**、同一个前缀、返回条目数**完全相同（8~10 个）**，唯一区别是调用
前 `PRAGMA case_sensitive_like = ON`：

| 档位 | 生产（pragma OFF） | pragma ON | 加速 |
|---|---|---|---|
| `xs`（1k 文件 / 2,990 行 changes） | 117 µs | 29.7 µs | 3.9× |
| `s`（40k 文件 / 49,800 行 changes） | **4,329 µs** | 31.3 µs | **138.4×** |
| `m`（240k 文件 / 438,800 行 changes） | 26.8 ms | 66 µs | 405.5× |
| `full`（1M 文件 / 1,995,000 行 changes） | **100.9 ms** | **32 µs** | **3,155.1×** |

**返回同样的条目，`xs` 117µs → `s` 4.3ms（膨胀 37 倍）→ `full` 100.9ms（膨胀 862 倍），
而加了 pragma 后各档位都停在 30µs 附近不动**——瓶颈完全来自"扫描了多少行"，
与业务逻辑无关。

### 4.4 一个特例：根目录（空前缀）改索引也救不了

`normalize_prefix("")` 得到空前缀，`like_prefix("")` 直接生成 `'%'`。空前缀在 GLOB 下
是 `*`，**首字符就是通配符，任何索引都无法下推**：

| 前缀 | 写法 | p50 @ `s` | 加速 @ `s` | p50 @ `full` | 加速 @ `full` |
|---|---|---|---|---|---|
| `assets/0000/0000/000/`（末级） | LIKE → GLOB | 3,851 → 15.4 µs | 250.6× | 88.4 ms → 15 µs | 6,029.1× |
| `assets/0000` | LIKE → GLOB | 3,859 → 330 µs | 11.7× | 89.0 ms → 1.5 ms | 58.5× |
| `""`（**仓库根**） | LIKE → GLOB | 8,667 → 7,613 µs | **1.1×** | 203.0 ms → 170.8 ms | **1.2×** |

也就是说，**修 B1 之后根目录仍然是全扫**。根目录必须靠 §6（B4）的 `parent_path` 方案解决——
这也说明 B1 与 B4 是互补的，不是二选一。

### 4.5 对 checkout 的直接影响

完整 checkout 要逐目录列一遍树。`full` 档位下目录总数 = 1（根）+ 100 + 10,000 + 100,000
= **110,101 个目录**，每个目录一次 `list_dir_head`，而每次 `list_dir_head` 因 B1 **外加
B4**（见 §6：它要读该目录的**全部后代**再在 Rust 里折叠成直接子项）而扫描整张 `head_entries`：

- 生产写法：`110,101 × O(1,000,000 行)` → **不可用**；
- 仅修 B1：仍然是 `110,101 × O(该目录后代数)`，总量约 `4 × 10^6` 行 → 十秒量级，
  但根目录那一次仍是全扫；
- 修 B1 + B4 后：每次只读直接子项（`parent_path` 等值查找）→ 总量 `1 × 10^6` 行。

这条链路的量级判断**已由 `full` 档实测确认，不是外推**：`list_dir_head_root` 为了返回
**1 个条目**，在 `s` 档（40k 文件）要 **35.5 ms**、`m` 档（240k）**206 ms**、
**`full` 档（1M 文件）762 ms**（见 §10，返回条目数恒为 1）。
checkout 的 110,101 次调用里，有 100 次是要付这个量级的（根 + 100 个 l1 目录，
两者返回条目数分别恒为 1 和 top）。

### 4.6 建议修复（P0，M2 开工前）

三选一，推荐组合：

1. **改 SQL（推荐）**：`repo.rs` 中所有 "前缀匹配" 的 `path LIKE ? ESCAPE '\'`
   改为**范围条件** `path >= ?pfx AND path < ?pfx_upper`，或改成 `GLOB`（`pfx*`）。
   注意 `%` / `_` / `*` / `?` / `[` 等元字符要按所选算子重新转义，并补等价性回归测试。
   **空前缀要单独处理**（见 §4.4）：直接跳过前缀条件即可，不要生成 `'%'`。
2. **改 pragma（最小改动）**：在 `db::open()` 里加
   `pragma_update(None, "case_sensitive_like", "ON")`。一行改动即可让现有 SQL 走上索引。
   语义上**更正确**（文件路径本就区分大小写），但属于全局行为变更，需评估其余 LIKE 用法。
3. 无论选哪个，都应新增一条**查询计划回归断言**：对关键查询跑 `EXPLAIN QUERY PLAN`，
   断言不出现 `SCAN changes`（防回归）。

> 本报告已用第二个方案做过**不改生产代码的验证**：在 `storage` 组的
> `*_cslike` 基准里对同一批 `repo::list_dir_at` / `repo::list_dir_head` 调用切换
> `case_sensitive_like`，量化收益见 §4.3 与 §10。

## 5. 根因分析（二）：热路径语句重复 prepare（B2，P0）

即使把索引修好，`file_at` 仍然是热路径的乘数项。证据链如下。

### 5.1 `env` 组微基准

| 基准 | p50 | 含义 |
|---|---|---|
| `stmt_prepare_uncached` | **7.3 µs** | 每次调用重新 prepare 同一段 ~150 字符 SQL |
| `stmt_prepare_cached` | **0.3 µs** | 走 rusqlite 语句缓存 |
| `stmt_index_lookup` | **3.8 µs** | 已 prepare 的索引点查（真实执行成本） |

> 单次"重新解析 SQL"（7.3µs）的代价约等于**两次真实索引查询**（3.8µs）。对一个上游
> 会放大几万倍的操作来说，这个系数是致命的。三个数字均来自 `xs`/`m` 档一致测量
> （`n=2000`，p50 在各档位间无差异——它是纯 CPU 行为，与数据规模无关）。

### 5.2 模型闭合

`repo::file_at(path, rev)` 的执行路径是：

```
file_at = 1 × last_change(path)                     ← 定位文件最近一次变更
        + covering_tombstone: 每个祖先 1 × last_change  ← ancestors("a/b/c/d/f.bin") = 4 个祖先
        = 5 次 query_row 调用
```

而 `last_change` 的实现是 `conn.query_row(SQL字面量, ..)`——**不经过 rusqlite 的
prepared-statement 缓存**（`query_row` 直接拿 SQL 字符串走 `prepare` + `query`，
而不是 `prepare_cached`），每次调用都要让 SQLite 重新解析一遍 SQL。

代入 §5.1 的实测值：`5 × (7.3 + 3.8) = 55.5 µs` ≈ 实测 `file_at_head` 的
p50 = **68 µs**（模型与实测吻合，缺口来自行映射、`String` 分配与 ancestor 拆分）。

这就是 `list_dir_at` 慢的第二个乘数：`last_changes_under` 拿到候选集合后，**要对每个
候选各做一次 `file_at`**。以 `sweep` 组的 `file_at_x{k}` 实测：代价随 k **线性**：

| 基准 | 候选数 | p50 @ `xs` | p50 @ `s` | p50 @ `m` | p50 @ `full` |
|---|---|---|---|---|---|
| `file_at_x1` | 1 | 98.4 µs | 102 µs | 72 µs | 69 µs |
| `file_at_x10` | 10 | 711 µs | 778 µs | 715 µs | 704 µs |
| `file_at_x100` | 100 | 7,211 µs | 7,984 µs | 7,580 µs | 6,968 µs |

> 单个候选恒为 ~70~100µs（比 `storage` 组裸调 `file_at_head` 的 68µs 略高：`sweep` 组每次
> 迭代还要构造/释放查询上下文，属固定开销）。**跨档位几乎不增长**（`xs`→`full` 在
> 0.7~1.0× 之间）正说明这一项与仓规模无关，是纯粹的"每候选固定成本"。

于是 `list_dir_at` 的代价模型是两项相乘：

```
T(list_dir_at) ≈ T(前缀扫描，受 B1 影响) + 候选数 × 5 × (prepare + lookup)
```

`full` 档位下根目录候选数 = 1,000,000 → 仅第二项就是
`1,000,000 × 100µs ≈ 100 秒`；叠加 B1 的扫描项后达到"不可用"。
**这个 100 秒的估算是报告撰写时按单价推出来的，随后被 `full` 档实测确认**：
`list_dir_at_root_head` 实测 **86.86 s**（§10），与估算同量级且偏低——
因为 `full` 档实测单候选单价是 69.5µs 而非 100µs（见上表）。

**这解释了为什么 `list_dir_at_l2_mid_cslike`（15.98ms）相对生产写法（15.66ms）几乎无改善
（0.98×）**：该前缀（`assets/0000`）的候选数 = 其子树下的全部条目 ≈ `5 × 5 × 8 = 200`
（`xs` 档），`200 × 100µs ≈ 20ms` 已经超过扫描项——**B1 与 B2 必须一起修**，只修索引会在
中等目录上再次撞墙。`s` 档同样只有 1.08×（180.9ms → 166.8ms）。

反过来，`list_dir_at_leaf_head`（候选数 = 8 个文件）在 `s` 档拿到 **9.31×** 加速
（9,934µs → 1,067µs）——候选数越小，B1 在总代价里的占比越高。
**这组"加速比随候选数下降"的对照，把 B1 与 B2 的相对权重直接量化出来了。**

### 5.3 建议修复（P0）

1. `last_change` / `covering_tombstone` 改用 `prepare_cached`（或把语句提到循环外
   一次 prepare 复用）。
2. 更好的做法是把祖先链检查合并成**一次**查询：用一条 `path IN (?,?,?,?) AND kind='dir'`
   的查询（或对规范化后的"祖先路径集合"做一次范围扫描），把 5 次往返压成 1 次。
3. `list_dir_at` 的候选存活判定改为**批量**执行（一次查询判定整批候选），
   消掉"每候选 5 次往返"的乘法结构。

## 6. 根因分析（三）：列目录要读"全部后代"（B4，P1）

### 6.1 现象

`list_dir_head` / `list_dir_at` 的 SQL 只做前缀匹配，**返回的是该前缀下的所有后代**，
真正"只留直接子项"的逻辑在 Rust 里：

```rust
// repo.rs: list_dir_head（生产代码）
let sql = "SELECT path, kind, blob_hash, size, mode, mtime, changed_rev
             FROM head_entries
            WHERE repo_id = ?1 AND path LIKE ?2 ESCAPE '\\'";
// ... 逐行在 Rust 里 split_once('/')，把更深的路径折叠成"隐式目录"
let (child, rest) = match rel.split_once('/') { ... };
if rest.is_some() { dirs.entry(child)...; }   // 更深层 → 只记目录名
else { entries.push(e); }
```

于是 `list_dir_head(root)` 为了产出 1 个条目，必须把**整张 `head_entries`** 读进 Rust 再折叠。
实测（`head_entries` 行数：`xs` 1,000 / `s` 40,000 / `m` 240,000 / `full` **1,000,000**；
"返回条目"由 fixture 布局精确算出）：

| 基准 | 前缀 | 返回条目 (xs/s/m/full) | p50 @ `xs` | p50 @ `s` | p50 @ `m` | p50 @ `full` | `full`/`xs` |
|---|---|---|---|---|---|---|---|
| `list_dir_head_root` | `""` | 1 / 1 / 1 / **1** | 726 µs | 35,499 µs | 206,084 µs | **762,149 µs** | **1,050×** |
| `list_dir_head_l1` | `assets` | 5 / 20 / 40 / 100 | 736 µs | 36,341 µs | 216,719 µs | 862,792 µs | 1,172× |
| `list_dir_head_l2` | `assets/0000` | 5 / 20 / 40 / 100 | 238 µs | 5,960 µs | 31,192 µs | 110,826 µs | 466× |
| `list_dir_head_leaf` | `assets/0000/0000/000` | 8 / 10 / 10 / 10 | 117 µs | 4,329 µs | 26,795 µs | 100,927 µs | 862× |

**返回条目数从 1 到 100 不等，耗时却都随仓规模线性膨胀**（文件数 1,000× → 耗时
466~1,172×）——这不可能用"结果集大小"解释，只能解释为"读了多少行"。
`dir_exists_at_head`（同样是前缀判定）在 `full` 档也要 **305.8 ms**，而它只需要一个布尔值。

### 6.2 `tree` 接口把它放大成一次全树遍历

```rust
// api/repos.rs: tree
let depth = q.depth.unwrap_or(1).clamp(1, 16);
let mut queue: Vec<(String, u32)> = vec![(prefix.clone(), 1)];
while let Some((dir, d)) = queue.pop() {
    let list = if use_head { repo::list_dir_head(&conn, repo.id, &dir)? }
               else { repo::list_dir_at(&conn, repo.id, &dir, rev)? };
    for e in list {
        if is_dir && d < depth { queue.push((e.path.clone(), d + 1)); }   // 只在 BFS 里限深度
    }
}
```

`depth` **只用来限制 BFS 是否继续下钻**，不参与任何 SQL。所以：

- `GET /tree?depth=1`（列仓库根目录）＝ 1 次 `list_dir_head("")`，但它要读**整张表**；
- `GET /tree?depth=16`（全树）＝ 110,101 次调用，每次读**该目录的全部后代**，总计约
  `4 × 10^6` 行（每一层的目录都把自己整棵子树重读一遍）。

HTTP 端实测印证：`tree_root_depth1`（列仓库根目录）@ `m` = **203.9 ms**、
@ `full` = **732.4 ms**；`tree_root_depth2` = 417.5 ms / **1.53 s**
（多下钻一层就再多付一次全表扫描的代价）。**注意 `depth=1` 本该是最便宜的一次调用，
却已经是秒级——因为 `depth` 根本没进入 SQL。**

### 6.3 建议修复

在 `head_entries` 上物化父目录路径，把"折叠"从 Rust 移到 SQL：

```sql
ALTER TABLE head_entries ADD COLUMN parent_path TEXT NOT NULL DEFAULT '';
UPDATE head_entries SET parent_path = ...;   -- 一次性回填
CREATE INDEX idx_head_parent ON head_entries(repo_id, parent_path);
```

`list_dir_head` 相应改为 `WHERE repo_id = ?1 AND parent_path = ?2`（等值，天然有界），
`tree` 也直接用 `parent_path` 逐层下钻。

**该方案已在真实 `full` 库上验证过查询计划**（`scripts/plan_evidence.py --demo-parent`，
用临时表 `head_demo` + `idx_head_demo_parent` 灌 200k 行）：

```
  SEARCH head_demo USING INDEX idx_head_demo_parent (repo_id=? AND parent_path=?)
```

✅ 关键列 `parent_path` 有界，无 `USE TEMP B-TREE`。仓库根对应 `parent_path = ''`，
因此 **§4.4 里"修 B1 也救不了根目录"的问题，正是由这一项解决的**。

> 依赖关系：B4 与 B1 互补而非替代。B4 让 HEAD 路径只读直接子项，B1 让**非空前缀**的
> 历史推导路径也能下推；两者都做，`tree` / `checkout` 才真正可用。

## 7. 根因分析（四）：`changes.blob_hash` 无索引（B5，P1）

### 7.1 现象

`apply_commit_tx` 在写提交时要算 `byte_delta`（用于 `repo_info` 的统计与配额），
做法是**对本次提交的每一条变更，反查全仓历史有没有引用过这个 blob**：

```rust
// repo.rs: apply_commit_tx
SELECT 1 FROM changes WHERE repo_id = ?1 AND blob_hash = ?2 LIMIT 1
```

而 `001_init.sql` 里 `changes` 表的索引只有两个：

```sql
CREATE INDEX idx_changes_path ON changes(repo_id, path, rev DESC);
CREATE INDEX idx_changes_rev  ON changes(repo_id, rev);
```

**`blob_hash` 上没有任何索引**，`EXPLAIN QUERY PLAN` 确认退化为按 `repo_id` 的整仓扫描：

```
  SEARCH changes USING INDEX idx_changes_rev (repo_id=?)     ← 关键列 blob_hash 无界
```

### 7.2 量化：提交延迟随仓规模超线性膨胀

`apply_commit_{k}` 的代价是 `O(k × 全仓历史行数)`：

| 基准 | 变更数 k | p50 @ `xs`（2,990 行） | p50 @ `s`（49,800 行） | p50 @ `m`（438,800 行） | p50 @ `full`（1,995,000 行） |
|---|---|---|---|---|---|
| `apply_commit_10` | 10 | 2.87 ms | 76.4 ms | 598.4 ms | **2.60 s** ᵃ |
| `apply_commit_100` | 100 | 28.8 ms | 800.9 ms | **5,913 ms** | **26.29 s** ᵃ |
| `apply_commit_1000` | 1000 | 284.6 ms | 8,092 ms | **67,499 ms** | **267.80 s** ᵃ |

`changes` 行数 `xs`→`m` 放大 **146.8×**，而延迟放大 **205~237×**；到 `full` 档行数放大
**667×**、延迟放大 **941×**（超线性，因为每行还要过一遍索引并读 `blob_hash` 列）。
这是本报告里第二严重的"随规模不可用"曲线：**`full` 档单次 `apply_commit_1000` 实测
267.8 秒**，一次正常提交就能拖垮服务——写路径在 `full` 档同样不成立。

> 这也解释了 harness 为什么必须在这批基准上降采样（§2.2 第 2 条）——不是为了好看，
> 而是 `full` 档单次 `apply_commit_1000` 在测量现场实测就要 **267.8 秒（4.5 分钟）**，
> 25 次迭代即两小时（`n=1` 已在表中用 ᵃ 标注）。

### 7.3 建议修复

1. **加索引**：`CREATE INDEX idx_changes_blob ON changes(repo_id, blob_hash);`
   注意 `blob_hash` 对目录行是 `NULL`，可用**部分索引**缩小体积：
   `CREATE INDEX idx_changes_blob ON changes(repo_id, blob_hash) WHERE blob_hash IS NOT NULL;`
2. **改语义（更根本）**：`byte_delta` 只是统计口径，不该在提交的关键路径上同步算。
   `blobs.refcount` 在方案里本就是"**可重建缓存**"（§3.1，truth = `changes` 表），
   把统计改成**异步/批量**（提交后由后台任务汇总，或直接由 refcount 维护过程顺带产出），
   关键路径上的这一项就可以整体删掉。
3. 若保留同步计算，至少要为单次提交批量查询：`blob_hash IN (?,?,...)` 一次查完。

## 8. 根因分析（五）：全局单连接互斥（B6，P1）

### 8.1 现象

```rust
// state.rs
pub struct AppState {
    pub db: Mutex<Connection>,      // ← 全局唯一连接
    ...
}
pub fn lock_db(&self) -> Result<MutexGuard<'_, Connection>, AppError> { self.db.lock()... }
```

所有请求（tree / log / changes / info / commit …）都要先抢这把锁，**并发度结构性恒为 1**。
SQLite 的 WAL 模式本来允许「多读并发 + 单写」，但这里被 Rust 侧的 `Mutex` 提前串行化了。

### 8.2 量化：加并发只增延迟，不加吞吐

并发度从 **8 → 32（4×）**：

| 基准 | c8 吞吐 | c32 吞吐 | 吞吐变化 | p50 变化 |
|---|---|---|---|---|
| `tree_root_depth1` @ `xs` | 886 req/s | 888 req/s | **+0.2%** | 5.4 → 23.7 ms（**4.4×**） |
| `tree_root_depth1` @ `s` | 28.0 req/s | 30.3 req/s | +8% | 166 → 644 ms（3.9×） |
| `tree_root_depth1` @ `m` | 5.4 req/s | 5.6 req/s | +4% | 882 → 3,199 ms（3.6×） |
| `tree_root_depth1` @ `full` ᶜ | 1.13 req/s | 1.21 req/s | +7% | 4,207 → 15,662 ms（3.7×） |
| `tree_hist_leaf` @ `s` | 109.2 req/s | 114.2 req/s | +5% | 44.4 → 183.6 ms（4.1×） |
| `tree_hist_leaf` @ `full` | 3.73 req/s | 3.79 req/s | +2% | 1,297 → 5,448 ms（4.2×） |
| `repo_info` @ `s` | 120.9 req/s | 125.3 req/s | +4% | 39.4 → 151.9 ms（3.9×） |
| `repo_info` @ `m` | 24.9 req/s | 23.2 req/s | **−7%** | 198.0 → 789.1 ms（4.0×） |
| `repo_info` @ `full` | 5.186 req/s | 5.186 req/s | **±0.0%** | 933 → 3,714 ms（3.98×） |
| `download_blob` @ `s` | 3,739 req/s | **8,157 req/s** | **+118%** | 1.39 → 2.75 ms（2.0×） |
| `download_blob` @ `full` | 3,481 req/s | **5,309 req/s** | **+52%** | 1.46 → 4.65 ms（3.2×） |

**并发度提升 4 倍，DB 相关端点的吞吐纹丝不动（甚至微降），而 p50 精确涨了 ~4 倍**——
教科书式的纯排队现象。`repo_info` @ `full` 是最干净的一例：**c8 与 c32 吞吐到小数点后
三位完全一致（5.186 req/s），吞吐比 1.000**，而 p50 从 933 ms 涨到 3,714 ms（3.98×）——
增加的 24 个并发请求在锁队列里排队，**对吞吐的贡献是零**。对照项 `download_blob`
同期拿到 **+52%~+118%** 吞吐，因为它的主体是 blob 文件 I/O、不长时间持有 DB 锁。
**这组对照把"瓶颈是锁而非 CPU / 网络"钉死了。**

更要命的是它是**结构性**的：`repo_info` @ `m` 的 c32 吞吐甚至低于 c8（24.9 → 23.2），
说明锁争用已经开始产生额外调度开销。再调并发、再加 CPU 核都无效。

> ᶜ `tree_root_depth1` 单请求在 `full` 档就是秒级，`conc` 组的 20 秒预算跑不完 64 个请求，
> 实际只采到 24（c8）/ 32（c32）个，因此其"吞吐"只反映短窗，不宜与外推值混用。

### 8.3 建议修复

属于 M2 的范畴（ACL / 锁会让这条路径更热），建议：

1. **读路径先拆出来**：用连接池（`deadpool-sqlite` / `r2d2` 风格）+ SQLite WAL，
   "多读并发 + 单写"的模型即可成立。存储层函数已经全部接受 `&Connection`，
   改动面主要在 `AppState` 与 `lock_db()` 的调用点。
2. 写路径仍需串行（SQLite 单写者），但可以用**更细粒度的写锁**，避免读请求被写请求阻塞。
3. 注意：B1/B2 修好后单次请求会快几十倍、锁的争用显著缓解，但**结构问题依然存在**，
   M2 之前要给出方案——M2 引入的 ACL 屏障会在此路径上再叠一层权限查询。

## 9. 根因分析（六）：refcount GC 的相关子查询（B3，P2）

### 9.1 现象与量化

GC 全量重建 refcount 的写法是"对每个 blob 各跑一次相关子查询"，代价
`O(blob 数 × 全仓历史行数)`；等价的 `GROUP BY` 全量聚合写法只需扫一遍 `changes`：

| 基准 | 写法 | p50 @ `xs` | p50 @ `s` | p50 @ `m` | p50 @ `full` |
|---|---|---|---|---|---|
| `refcount_correlated_1blob` | 相关子查询（1 个 blob） | 217 µs | 5,422 µs | 52.2 ms | 199.1 ms |
| `refcount_correlated_10blob` | 相关子查询（10 个 blob） | 1,900 µs | 56,799 µs | 522.7 ms | 2.04 s |
| `refcount_groupby_all` | 一次 `GROUP BY` 全量重建 | 3,878 µs | **55,175 µs** | 453.0 ms | **1.79 s** |

**关键对比**：`s` 档下 `refcount_groupby_all` **一次重建全部 2,000 个 blob** 只要
**55.2 ms**，而相关子查询写法**只算 10 个 blob** 就要 **56.8 ms**；到 `full` 档这个
反差更直接——`GROUP BY` 重建全部 **4,000** 个 blob 用 **1.79 s**，相关子查询
**只算 10 个** 就要 **2.04 s**。按样本单价线性外推，相关子查询重建全部 4,000 个 blob
需要 **~797 秒（≈13 分钟）**，而 `GROUP BY` 写法不到 2 秒（外推行见 §10 的 ᵇ 标注）。

### 9.2 建议修复

`refcount` 本就是可重建缓存（§3.1），全量重建直接用 `GROUP BY` 写法：

```sql
SELECT blob_hash, COUNT(*) FROM changes
 WHERE repo_id = ?1 AND blob_hash IS NOT NULL AND op <> 'delete'
 GROUP BY blob_hash
```

代价 O(一次扫描)。另外方案 §3.4 的 `gc_queue` 增量路径应保证**不需要**全量重建，
全量重建只作为运维/校验入口——这一点建议在 M2 的维护接口里明确写清。

## 11. 瓶颈清单

### 11.1 汇总表

| 编号 | 瓶颈 | 一句话机制 | 关键实测证据 | 影响面 | 修复 | 优先级 |
|---|---|---|---|---|---|---|
| **B1** | 前缀 `path LIKE 'pfx%'` 未下推索引 | `case_sensitive_like=OFF` 时 SQLite 无法把前缀 `LIKE` 变成索引范围扫描，退化为按 `repo_id` 扫全仓 | 同一函数只切 pragma：`list_dir_head` @末级目录 `xs` 117µs → `s` 4.3ms（**138×**）→ `full` 100.9ms（**3155×**）；GLOB 重写在 `s` **250.6×**、`m` **1145×**、`full` **6029×** | 所有列目录（HEAD + 历史 + `tree` + `checkout`） | 改用范围条件 / `GLOB`；或 `PRAGMA case_sensitive_like=ON`；空前缀单独处理 | **P0** |
| **B2** | 热路径语句重复 prepare | `last_change` 用 `conn.query_row(SQL字面量,..)`，绕开 rusqlite 语句缓存；每次 `file_at` = 5 次未缓存语句 | `stmt_prepare_uncached` 7.3µs vs `cached` 0.3µs；`5 × (7.3+3.8) = 55.5µs` ≈ 实测 `file_at_head` 68µs；`file_at_x{1,10,100}` 各档位严格线性、跨档位几乎不增长 | `list_dir_at` 每个候选、`file_at` 每次调用 | `prepare_cached`；再把祖先链检查合并成一次查询 | **P0** |
| **B3** | refcount GC 相关子查询 | 每 blob 一次相关子查询，`O(blob × 全仓历史)` | `s` 档：`GROUP BY` 全量重建 2,000 blob = **55.2ms**；相关子查询只算 **10** 个 blob 就要 56.8ms。`full` 档：`GROUP BY` 全量 4,000 blob = **1.79s**，相关子查询只算 10 个 = **2.04s**（外推全量 ~797s） | GC / 运维重建 | 改 `GROUP BY` 全量写法；`gc_queue` 增量路径保证不必全量重建 | P2 |
| **B4** | 列目录要读"全部后代" | SQL 只做前缀匹配，返回**所有后代**，再在 Rust 里折叠成直接子项 | 返回条目恒定（root 恒 1 项）、耗时随规模膨胀：`list_dir_head_root` `xs` 726µs → `s` 35.5ms → `m` **206ms** → `full` **762ms** | `tree?depth=1`、`checkout`、`dir_exists` | `head_entries` 加 `parent_path` 列 + `idx_head_parent(repo_id, parent_path)`；已在 full 库验证计划（§6.3） | P1 |
| **B5** | `changes.blob_hash` 无索引 | `apply_commit_tx` 每条变更反查整仓历史算 `byte_delta` | `changes` 行数 667× → `apply_commit_1000` 延迟 **941×**（`m` 档 **67.5 s**、`full` 档 **267.8 s** /次）；`EXPLAIN` 显示按 `repo_id` 无界 | 所有 commit（写路径） | 加部分索引 `(repo_id, blob_hash) WHERE blob_hash IS NOT NULL`；更根本是把 `byte_delta` 移出提交关键路径 | P1 |
| **B6** | 全局单 `Mutex<Connection>` | `AppState.db` 是唯一连接，所有请求串行；并发度结构性恒为 1 | 并发 8→32（4×）：DB 端点吞吐 +0.2%~+8%（`repo_info @m` **−7%**、`repo_info @full` **±0.0%**），p50 涨 ~4×；同期 `download_blob` **+52%~+118%** | 全部 API 的并发能力 | 读路径改连接池 + WAL；写路径保留串行但细化粒度 | P1（M2 处理） |

### 11.2 修复顺序与依赖

```
B1 + B2  ──┬─→ 列目录类路径恢复可用（tree / checkout）
B4       ──┘
           └─→ B1 修好后根目录仍需 B4；B4 修好后非空前缀仍受 B1 影响（互补，非替代）

B5       ────→ 写路径可用（commit 不再随仓规模线性劣化）
B6       ────→ 并发能力（M2 引入 ACL 后此路径更热，须在 M2 内解决）
B3       ────→ 运维重建时间（可延后）
```

建议：**B1 + B2 + B4 + B5 合并为一次 schema 迁移 + 一次 `repo.rs` 重构**（改动集中在
`repo.rs` 的查询构造与 `001_init.sql`/新迁移），一次性做完并补查询计划回归断言
（§4.6 第 3 条）。B6 独立在 M2 内处理，因为它会改 `AppState` 与全部 handler 的取锁方式。

### 11.3 已验证**不是**瓶颈的部分（避免后续误判）

| 项 | 实测（`xs` / `s` / `m` / `full`） | 结论 |
|---|---|---|
| `last_change`（单路径最近变更） | `EXPLAIN`：`idx_changes_path (repo_id=? AND path=? AND rev<?)` ✅ 有界 | 索引正确，无需改动 |
| `log` 分页 | 存储层 `log_page_100` 43 / 59 / 96 / **50** µs；HTTP `log_50` 0.49 / 0.59 / 1.2 / **4.9** ms | 存储层完全平坦；HTTP 侧 `full` 档升到 4.9 ms 但绝对值仍低，不构成瓶颈 |
| `changes` 增量窗口 | 293 / 366 / 770 / **377** µs（100 修订） | 线性且量级很小（`full` 档反低于 `m`，属采样噪声） |
| `blobs/missing`（差异探测 1000 路径） | 6.5 / 7.1 / 6.7 / **6.8** ms | **完全平坦**，实现健康 |
| `download_blob` | 287 / 339 / 288 / **289** µs | 平坦；且是唯一能随并发扩展的端点（B6 的对照项） |
| `file_at`（单文件读取） | 68 / 73 / 138 / **69** µs | 增长温和甚至回落，修 B2 后可再降 |
| `login_argon2id` | 115.0 / 120.9 / 113.7 / **106.6** ms | **故意慢的密码哈希，不是缺陷**；与存储无关，各档位恒定 |
| `health` | 96 / 113 / 102 / **97** µs | 纯框架开销，量级正常 |

## 12. 复现方式

```bash
# 1) 一键跑全档位（造数 → 压测 → 原始 JSON 落到 bench-results/）
#    xs/s/m 约 10 分钟；含 full 档需数小时，full 档用较小 iterations/budget
scripts/m15_bench.sh --scales xs,s,m --iterations 25 --budget 12 --concurrency 8,32
scripts/m15_bench.sh --scales full    --iterations 10 --budget 20 --concurrency 8,32

# 2) 汇总成 markdown 表（本报告 §10 的结果表就是它的输出）
python3 scripts/m15_summary.py bench-results > /tmp/m15-tables.md

# 3) 采集查询计划证据（本报告 §4 的证据来源）
#    产物：bench-results/plan-evidence-full.txt
python3 scripts/plan_evidence.py /tmp/b-artifact-fixtures/full
python3 scripts/plan_evidence.py /tmp/b-artifact-fixtures/full --demo-parent  # 附 B4 的 parent_path 对照

# 单档位、指定分组；--reuse 跳过造数直接复用已有 fixture
scripts/m15_bench.sh --scales xs --only storage,sweep --reuse
```

`m15_bench.sh` 关键参数：

| 参数 | 含义 |
|---|---|
| `--scales` | 档位列表，子集：`xs,s,m,full`（默认 `xs,s,m`） |
| `--only` | 只跑指定分组，可选：`env` `storage` `sweep` `http` `conc`；不传则全跑 |
| `--iterations` | 采样次数上限（超预算即早停，实际 `n` 记入 JSON） |
| `--budget` | 单基准时间预算（秒），触顶即停采并标注实际 `n` |
| `--concurrency` | HTTP 并发档位列表（B6 证据来自 `8,32` 对照） |
| `--heavy` | 重基准采样策略（`auto` 让 `full` 档自适应降采样） |
| `--reuse` | 复用已有 fixture，不重造（重测调参时用，省 6 分钟/档） |
| `--force` | 强制重造 fixture |

产物：

| 文件 | 内容 |
|---|---|
| `bench-results/env.json` | 压测环境（CPU / 内存 / 工具链 / 数据目录） |
| `bench-results/fixture-<scale>.json` | 造数摘要（规模、DB 体积、耗时） |
| `bench-results/m15-<scale>.json` | 原始指标（逐基准 p50/p95/p99/n/规模/备注） |
| `bench-results/plan-evidence-<scale>.txt` | 关键查询的 `EXPLAIN QUERY PLAN` 原文（§4 证据） |
| `bench-results/run.log` | 完整运行日志 |
| `bench-results/gen-<scale>.log` | 造数日志（含 fixture 明细） |

> 复现提示：fixture 默认落在 `$TMPDIR/b-artifact-fixtures/<scale>`，`m15_bench.sh`
> 每次运行会 clonefile 出一份 `<scale>-run` 副本再压测，因此同一个 fixture 可被
> 反复复用而不被压测过程污染；`--reuse` 跳过的正是造数那一步。
